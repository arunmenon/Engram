## Code and test inspection (after the walkthrough)

- **Catalog preserves checks.** `catalog.py` advertises only packs `load_registry` can compose; `Content.unique_ids` rejects unavailable or duplicate packs (API returned 422 "Unavailable domain packs: ['nope']" and "Select each domain pack only once", `api-probes-2.json`). `test_composition_uses_selected_catalog_and_keeps_shadow_dependency_collision_checks` covers shadowing, missing dependency and name collision; `test_both_domains_compose_with_independent_authored_extension` covers crm+pdlc. The frontend has no PDLC branch (the only `pdlc` literal is the stories blurb); options come from `pack_catalog`.
- **No-lifecycle packs.** `api.py` readiness requires `["identity","lifecycle"]` only when `has_lifecycle(pack)`. My synthetic Supplier directory copy showed only "I checked the fields that identify each entity" and accept enabled after that single box (`s8-no-lifecycle-review.png`).
- **Explanation evidence binding.** `explain.py context_for` builds the subject from `types.nodes`/`types.edges` sorted by name at the requested index, or the pack summary; the route re-reads the record at the requested revision and rejects stale revisions (409 "Draft changed. Reload before continuing.") and out-of-range indexes (422 "This item is no longer available"); the response echoes revision, scope and index. Note: node/edge index is positional over sorted names, so a renamed or added type shifts indexes; the revision fence makes this safe today.
- **Grouped acknowledgements.** The UI ticks one box per category, but `onAccept` submits the exact change IDs; `review` rejects a subset (409 "Acknowledge each pack change before accepting this revision"), unknown IDs (422), missing removals (409 "Explicitly review each proposed data removal first") and unknown removals (422). Confirmed on both Northstar and CRM copies.
- **Originals intact.** `tests/fixtures/packs/crm/crm.pack.yaml` unchanged in git; the catalog copy `src/context_graph/workbench/packs/crm.pack.yaml` keeps the email-keyed Contact; expected answers and review evidence directories untouched.
- **Implementer self-check note:** the M2b copies were seeded from the Codex whole-flow snapshots, as mine were; M2a's drafts are synthetic. Neither is independent acceptance, as their READMEs state.

## Verdicts

- **M2a functionality: pass.** Catalog from capabilities, no frontend PDLC branch, composition/collision/dependency checks retained and tested, unknown/duplicate selections rejected, selection survives save/reload/sign-in, no-lifecycle packs need only identity confirmation, original fixtures intact.
- **M2b functionality: revise.** Scoped explanation, revision fencing, grouped acknowledgements with server enforcement, trust in setup and Continue skipping 3b all pass. F1 is a regression of the accepted M1a behaviour; F2 and F3 break "removals remain explicit / one editor" and "back/forward preserve input".
- **Visual clarity: revise** (F4, F8, F2). The understood/decide split and grouped changes are a real improvement; the page is still long and the catalog is hidden.
- **AI helpfulness: not exercised live.** All explanations here are fixture output and establish transport and binding only. F04 stays open; F5 adds a trust-decision instance of the same problem. Unsupported-answer rendering is honest.
- **Accessibility (tested scope): pass with notes.** Keyboard reaches every control; 430 px layouts have no horizontal overflow (Delivery review 4,375 px, setup 2,060 px, Northstar with request 5,251 px); focus defects F2/F9; no screen-reader run and no WCAG claim.

## Recovery-state matrix

Exercised: save/reload/sign-in, tenant switch, selection switch, consent change both ways, restore prompt and restore, failed send (fixture author), late response, explanation failure, server stale-revision and index fences. Not exercised: "Stop waiting", save during polling, legacy record restore, sign-out clearing, screen reader, live provider, sandbox/Spanner, approval.

## Conclusion

Do not proceed to M3 yet. Blocking fixes: **F1** (prepared request and answer lost after a failed send, generic banner), **F2** (removal "Keep this data" path), **F3** (acknowledgement ticks lost on navigation). These are small, contained changes in the review step and should be re-verified on fresh copies with a failing author fixture before M3 starts. F4 should be fixed before any demo but does not block M3 design work. F5/F04 remain open as previously recorded and are not closed by fixture explanations or passing tests. No product code or expected outcomes were changed by this review.
