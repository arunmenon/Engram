Engram architecture from first principles
1 · Architecture fundamentals

Start with what runs where

Engram is the application. Spanner is its managed storage and query backend. A request reaches Engram first; Spanner does not interpret ontology packs or run Engram workers.

Engram turns recorded activity into connected knowledge that an application can retrieve with evidence. It keeps the original event history and builds a graph that makes relationships easier to query.

The whole flow, before the details

Write request → accepted event in ledger → asynchronous workers → graph records → retrieval request → structured context.

“Asynchronous” means the write can finish before the workers finish. The ledger is the durable history; the graph is a derived view of that history.

RUNS IN ENGRAM

The application side

HTTP API service — accepts writes and read requests
Pack loader and shared engine — determine allowed behavior
Five worker loops — process accepted events
Storage adapters — turn engine operations into Spanner calls
Embedding and LLM providers — used by relevant paths
STORED OR EXECUTED IN SPANNER

The database side

Event ledger — accepted event documents
Consumer state — progress and pending work
Graph tables — nodes and relationships
Search indexes — text and Entity vectors
EngramGraph — property graph over graph tables

Two different kinds of state: the ledger records accepted activity. The graph is a derived representation built later by workers. They can live in the same Spanner database while being written in separate transactions.

Read it with one event

E17 is stored once in Events. Each group can have its own pending E17 row in ConsumerDeliveries. Acknowledging E17 removes that group’s pending delivery, while the Events row remains. ConsumerCursors records delivered progress per shard; it does not prove every earlier delivery completed.

The write request ends at the ledger

The API validates and accepts an event. It does not synchronously run all five workers before returning the ingestion receipt.

HTTP inputPOST /v1/events; batch/import routes also exist. Signed webhooks have source adapters.
→
Engram checksBody bounds, event envelope, declared event and applicable pack contract.
→
Ledger transactionResolve retry/conflict; record eligible event and acceptance identity.
→
HTTP receiptReturn identity, position and created/duplicate outcome.

Envelope

Shared fields such as event identity, event type, timestamp, session and agent/source context.

Payload

The domain-specific JSON object. Pack contracts define the fields required for supported event types.

Server acceptance identity

For a bound runtime, this records the authorized tenant/database/binding, bundle identity, engine revision and normalized request fingerprint.

The caller cannot freely supply these server-owned authority fields.

Important outcomes: an identical accepted retry can return duplicate; conflicting reuse of its identity returns a conflict; invalid new input is rejected. Batch writes can span transaction-sized chunks, so inspect per-item outcomes rather than assume the entire large request was one atomic transaction.

{

Identical content with the same ID is a duplicate and does not append another event. Reusing that ID with different content is a conflict (409). Neither a created receipt nor a duplicate receipt says the graph is ready.

5 · Architecture fundamentals

What one ledger row represents

An Events row is the durable record from which consumers load an accepted event. The delivery notification contains its identity; the worker loads the document separately.

Events row — simplified physical picture
event_id → primary key
document → normalized event envelope plus payload
acceptance → server-owned interpretation identity when bound
commit_ts + batch_index + event_id → ledger position
shard → calculated from session ID
summary / keywords / search_text → searchable derived fields
in_log / in_session_index / dedup_active → lifecycle flags

Source time

The event timestamp describes when the activity occurred at its source.

Ledger position

The Spanner commit timestamp, batch index and event ID describe accepted ledger order. They are not the same as source time.

Shards distribute the time index. The subscription defaults to 16 logical shards; a session hashes to a shard. Each consumer group tracks a cursor for every shard.

The ledger is not the graph. A row in Events does not itself create a GraphNodes row. Search/enrichment fields and retention flags can change; “ledger” does not mean every column remains immutable forever. The acceptance identity protects interpretation of accepted content.

Where E17 lives after acceptance

Its accepted document contains the tool event and content. A delivery notification can carry only its identity; a worker fetches the document when it needs the payload.

Conceptual valueExample or explanation
Event identityE17, the UUID shown on page 4
Activity groupingsession-17 / assistant-17 / trace-17
Source time2026-10-09T09:00:00Z
Accepted positionAssigned by Spanner storage; not the source timestamp
ShardStorage-assigned polling partition; not chosen by the caller
Lifecycle flagsMarkers used by storage/maintenance policy; not the business outcome of a deployment or test

Sharding divides event delivery/index work into partitions. A group tracks its delivered position separately for each shard. These labels explain the concepts; they are not a literal SQL INSERT or complete column listing.

6 · Architecture fundamentals

How consumer groups actually run

The worker is running Engram code. The group is a named progress record. The subscription adapter connects them to the ledger. With this backend, the worker polls Spanner instead of consuming Redis Streams.

First: what is a worker, and why do we need five roles?

A worker is a running piece of Engram code that handles a particular job after an event is accepted. For example, saving “a test failed” is one job; creating a TestRun in the graph is another. Keeping these jobs separate lets a slow extraction job avoid blocking the initial write request.

The five names below describe jobs, not packs. They can handle activity from optional domain packs as well as the original agent-oriented use cases. A consumer group is each job’s durable progress record; it does not define what that job computes.

Worker nameWhat it does, in ordinary languageWhat that means for a domain pack such as PDLC
Graph projectionBuild the connected records explicitly described by an event. Read IDs and fields, then create or update nodes and links.A test-result payload becomes TestRun and TestCase records under PDLC rules. The same worker also builds the common Event record.
Session extractionRead accumulated session content and ask a model to identify entities and, when enabled, user information. It waits for a session trigger.PDLC activity can be part of that session. This does not automatically extract every PDLC artifact or enable user profiling.
EnrichmentAdd useful labels and search-related annotations to an Event, such as keywords, importance and an optional embedding.A PDLC test or deployment event can receive these shared annotations too. This worker does not decide the test/deployment outcome.
ConsolidationPeriodically condense accumulated activity into summaries and apply maintenance policies.It may summarize eligible activity containing PDLC events. It does not immediately summarize every event or create domain lessons automatically.
Pack extractionRead relevant prose using instructions declared by a selected pack; ask a model for allowed knowledge proposals.A PDLC design section may yield a proposed Decision or Constraint. A test-result fact still comes from its producer, not a model guess.

Important: receiving an event does not mean every job must produce something. A job can wait for a later trigger or find no applicable rule and finish handling that delivery.

First distinguish the three pieces

Worker: an application loop that performs a job, such as graph projection. Engram starts the loop; Spanner does not execute it.

Consumer group: a name such as graph-projection, with its own durable cursors and pending deliveries. It is not a separately running database service.

Subscription adapter: Engram code implementing “read new”, “read pending”, “acknowledge” and “claim abandoned work” using Spanner transactions.

Workers may run in separate application processes. Test runners can host their ordinary loops together; the logical group boundary is independent of the process layout.

Diagram 1 Where the pieces live

The SDK is Google’s library, not an Engram SDK. Engram’s adapter calls google-cloud-spanner objects such as the database handle and transaction. The library handles service communication and sessions. It runs inside Engram; it is not an extra deployed service.

Startup creates the Client, selects the Instance and Database, and gives the database handle to the adapters. The worker also uses separate event-log and graph adapters to load documents and write results. The subscription adapter only handles delivery bookkeeping.

Diagram 2 One polling and processing cycle

If no batch is available: the adapter waits briefly and polls again, up to the caller’s blocking timeout. An empty read allows the worker’s idle hook to run. This is polling through SDK/SQL calls, not a Spanner push notification or change-stream subscription.

Why separate cursor and pending records? The cursor says “we have delivered up to here”. Pending records say “these deliveries are not yet acknowledged”. Advancing the cursor is not proof the graph write finished.

Diagram 3 One event can be at five different stages

These are illustrative states for the same event E17, not observations from a test run. Every group has its own progress; acknowledging one group does not complete the others.

Groups versus consumers: consumers in the same group share its transactional delivery bookkeeping. Different groups independently receive the event for their own responsibilities. Do not infer a deployment-wide ordering between the five workers.

What happens after failure or restart

Before acknowledgement: a failure leaves the delivery pending. A crash after a graph write but before acknowledgement can cause that work to be delivered again. Writes therefore need retry-safe identities and behavior.

On startup: the worker ensures the group exists, claims eligible stale deliveries, drains its pending items, then enters the new-event loop.

Repeated failures: the pending-drain path tracks attempts and can explicitly move a repeatedly failing item to ConsumerDeadLetters.

Current limitation: ordinary main-loop processing failures are not guaranteed a live retry. The generic pending-drain call is at startup; some transient storage operations separately retry in place.

Spanner’s role is durable coordination and storage. Engram owns the loop, processing code, acknowledgement boundary and recovery policy. Group completion also does not prove every expected semantic output exists; the verification must inspect graph writes, evidence and retrieval.

Where these workers actually live

These are the shared roles described at the start of this page. Their names describe their responsibilities; pack selection determines the supported branches they use, as shown below.

They are Engram application code, started with the worker entry point and a selected consumer role. Spanner runs their database operations; it does not host or execute the worker loops. The logical roles below can run as separately started processes. This picture is not a requirement for five separate machines.

Each role uses its own group progress over the ledger. The five names are parallel responsibilities, not five sequential phases. A process calls the subscription adapter to get work, the event-log adapter to load content, and the graph adapter when it needs graph operations.

How optional packs use these same workers

Think of workers as the machinery and packs as declarations the supported machinery can follow. Selecting PDLC adds its types, payload contracts, projection rules and extraction profiles. It does not create a separate PDLC engine or require a PDLC version of every worker.

What “dynamic” means here

The generic projector can interpret supported rules from a selected pack, and the pack-extraction worker can use that pack’s supported profiles. A new domain pack can reuse those mechanisms without custom wiring for every pack pair.

Session extraction, enrichment and consolidation still contain specialized implementations. A pack cannot invent a new worker capability by naming it in YAML. New behavior outside the engine’s supported contracts needs an implementation and verification first; an unsupported requested handler must fail validation.

Pack selection is assembled during startup or activation. It does not start worker processes, guarantee their providers are ready, or make every event produce all possible outputs.

8 · Architecture fundamentals

Worker deep dive: graph projection

Build the graph representation of accepted facts. This worker uses code and declared rules—not an LLM deciding what happened.

Why this worker exists

The ledger tells us that something happened, but a row of event JSON is awkward to follow as a network of connected facts. We need a graph that lets us move from a test result to its test, or from a review to its change.

Its job: Read the accepted event and apply explicit rules to build those graph records.

You should get: An Event that preserves the activity, plus any matching domain objects and links. The rules—not a model guess—decide what gets created.

By the end, you should be able to answer: How did this payload become these particular nodes and arrows?

Which graph schema does projection use?

Schema versus records: a schema defines allowed kinds of nodes, their identities/properties and relationship endpoints. The worker writes particular records using those definitions. It does not invent a new ontology each time it reads an event.

Where the schema comes from: at startup, Engram loads mandatory core plus selected compatible packs, validates their declarations and resolves supported capabilities. That checked configuration governs these writes. Spanner stores the records in GraphNodes and GraphEdges; EngramGraph exposes those tables as a graph. A type such as TestRun is not a separate Spanner table.

Now look inside the implementation

A delivery identifies an accepted event. Projection loads its document and plans the common Event plus applicable activity links. Selected domain packs can add deterministic rules for the same event. An artifact is a domain object such as a TestRun; it is separate from the Event recording that the result arrived.

Before and after: a failed test

Supplied: test identity, run identity, outcome = failure, commit SHA and any explicit change/requirement references in a valid finished-test payload.

PDLC rule: create TestCase and TestRun; connect TestRun → EXECUTES → TestCase. Add only applicable declared RAN_AGAINST / VERIFIES links.

After: core Event plus domain records. Failed is a test outcome, not a worker exception. An identity-only referenced node can be a placeholder; it is not proof that its own source event was received.

Partial success, retry and acknowledgement

Core Event writes can succeed before a pack plan fails. The implementation can dead-letter an individual failed pack application; a non-transient batch error can fall back to individual application. Therefore an acknowledged delivery does not by itself prove every domain artifact was written.

A write-before-ACK crash can leave work pending for redelivery. Storage writes and delivery acknowledgement are separate operations; do not portray them as one atomic transaction or an unconditional live-retry guarantee.

What retrieval can use

Event/context retrieval can use activity nodes and links. Artifact retrieval can use projected domain nodes, their permitted relationships and recorded evidence. A missing domain output cannot be repaired by assuming the core Event proves it exists.

Worker deep dive: session extraction

Read accumulated session content and turn model results into structured entities, with user-specific information only when enabled.

Why this worker exists

Useful information is often buried in conversation or activity text: a service name, a person, or a stated preference. It is not always supplied as structured graph fields.

Its job: Read enough session content, ask a model for structured information, then resolve and store the supported results.

You should get: Entities connected to source activity; optional user information only when the user capability is enabled. Model output is conditional.

18 · Architecture fundamentals

Tenant binding and failure boundaries

Pack composition and tenant isolation solve different problems. A valid bundle describes behavior; an authorized binding determines which tenant database that runtime may access.

Bound runtime association
Tenant identity + authorized database resource + binding ID
+ fixed pack bundle identity + engine revision + ownership epoch
The epoch distinguishes the authorized runtime generation. TenantControl is checked by fenced operations.

Database boundary

The agreed design uses a separate Spanner database per tenant. The same association must govern writes, subscriptions, workers, graph reads and response handling.

Service boundary

Private bound-tenant machinery exists. The public shared multi-tenant factory currently refuses startup. Database separation does not automatically provide safe tenant dispatch.

What happens when work fails

Pending deliveries are durable. Startup claims eligible stale deliveries and drains pending work; repeated failures can be dead-lettered. Selected transient storage operations retry with backoff. Projection defers acknowledgement until its flush boundary.

An important code boundary: the ordinary main loop reads new deliveries. Its pending-drain call is at startup; a generic processing exception can remain pending rather than automatically receiving a live retry. Do not draw recovery as an unconditional self-healing loop.

Zero pending lag alone does not prove every semantic output is correct. Verification must check the graph, evidence and retrieval. This guide does not implement tenant dispatch or change recovery behavior.

Two tenants, concretely

RuntimeAuthorized data and behavior
Tenant ADatabase A; core + user. Writes, deliveries, graph operations and reads must use A’s binding.
Tenant BDatabase B; core + PDLC. Those operations must use B’s binding, even if event IDs happen to match.

A query from A must not switch to B’s database because its text mentions B or its body names a database. Authentication and the authorized binding establish that boundary.

An epoch is a runtime-generation number. When ownership moves to a newer generation, an older runtime is stale. Fencing means rejecting guarded operations from that stale generation. Database-per-tenant storage and safe shared API routing are separate requirements; the public dispatcher remains unsupported today.
