# Foundation necessity and simplicity review

## Verdict for stakeholder decision

**Keep the isolation, accepted-event identity, source authority, optional-capability selection and transaction safeguards. Simplify the experiment tooling first. Defer further expansion of unused property-update machinery, public dispatch and peripheral maintenance work.** The foundation contains more than G01–G03 need, but “not exercised by these demos” is not sufficient reason to delete an agreed product safeguard.

This is one bounded necessity review of walkthrough `27b4ba861814163d4292a950ddaae484a4282d82` → snapshot `f6fd87ce1086522bdc6fea1846d92ab9d6f50f31`, with current gate documents and representative source/tests. It is distinct from the earlier correctness review. No code/test changes, test execution, cloud calls, issue updates, migration analysis or new agent delegation occurred. Only this report was written. Recommendations below require stakeholder approval; none has been implemented.

The comparison contains **64 changed runtime files, 4,851 added and 611 removed runtime lines**; **16 added scripts, 8,694 lines**; **49 test/fixture files, 6,874 additions and 12 removals**; and a **4,204-line lockfile**. **1,673 retained-run files account for 531,445 added text lines**, excluding binary sizes. These are distinct categories: raw evidence is not runtime complexity. G01–G03's PDLC mappings, goal drivers and retrieval fixes were already in the walkthrough parent, so they are dependencies/context, not new snapshot source deltas.

The gate document currently records a fresh local pass and G01 rerun, interrupted G02 and pending G03/publication. I did not reverify those executions here. Neither this assessment nor old review notes converts the paused gate into a completed gate.

## Prioritized findings and simpler options

### 1. Highest-value simplification is the experiment support layer

The drivers import `load_credentials` from `scripts/engram_spanner_compat.py:40`, a runner of over 2,200 lines; `runtime_settings` from `engram_spanner_tenant_runtime_cases.py:21`; `durable_json`/`fingerprint` from `engram_spanner_tenant_control.py:29,43`; and `await_settled` from a case module. These small utilities pull historical runner imports into a new goal's dependency closure. The inventory correctly says static import does not mean runtime execution, but the coupling makes that distinction harder to maintain and setup less portable.

G02/G03 drivers are near copies, including `DemoAuthentication:69`, server/five-worker setup, retrieval helper, extraction-log observation and final ownership cleanup. G01 has its own corresponding wrapper at line 74. Repeating scenario assertions is useful; repeating security/cleanup plumbing is a drift risk. The concrete smaller design is one **ordinary shared helper module**, with the existing functions moved unchanged and scenario fixtures/assertions kept in their current goal files. New goals should call those functions, not inherit an extensible harness class or introduce a runner schema. Historical archived sources stay untouched. This is a recommendation, not a requirement to refactor before finishing the paused gate.

### 2. The strict property language has no demonstrated G01–G03 consumer

`domain/ontology.py:324` introduces a second opt-in property form; `pack_properties.py:26-65` distinguishes missing/null/invalid and supports per-cell selection; `pack_removals.py:16-40` validates explicit deletion. Searching current pack declarations found the feature in `tests/fixtures/pack_contracts/propertylab.pack.yaml`, not core/memory/user/PDLC manifests. Thus its correctness tests cannot establish that G01–G03 need its whole policy surface.

Protected-field clearing is preserved in the small-goal inventory, so this is **later justified capability**, not proven arbitrary code. Freeze its feature surface until that scenario is selected. If the stakeholder only needs explicit deletion, the existing `remove_properties` channel plus protected-field validation is a concrete narrower option. Do not silently substitute it for the richer contract or remove existing behavior during this review.

### 3. Separate public-dispatch ambition from the binding actually used

`api/tenants.py:31` intentionally refuses public startup; its internal dispatcher adds child lifecycle, routing and request-drain accounting. G01–G03 use a local single-bound wrapper with actual `TenantCatalog.authenticate` and `TenantResponseGuard`, not the multi-child dispatcher. The agreed tenant requirement supports retaining binding/fences/catalog now; it does not require completing the dispatcher before a release/deployment journey. Defer that extension to an explicitly selected G12/G13 step. Avoid counting the prototype's presence or imported code as isolation acceptance.

### 4. Several apparent duplicate identities/checks buy different guarantees

`ActiveBundle.identity` identifies schema/processing selection; `TenantBinding.bundle_digest` additionally identifies engine/configuration policy. The earlier G02 oracle error confused them, but collapsing them would remove a distinction that protects processing authority. A documentation/variable-label clarification is safer than changing stored receipt semantics.

Likewise, startup settings checks, per-transaction ownership checks, authoritative worker reads, terminal ACK/DLQ checks and final response authorization cannot be reduced to one “validated” flag. They run across different mutation/cancellation/concurrency windows. `SourceTrustPolicy.trusted()` rechecking an event against typed provenance protects direct planner composition; it does not refetch storage. Keep these boundaries.

`ActiveBundle.registry` reconstructs a detached view (`pack_bundle.py:65-70`), and construction uses it in several places. Reusing a local view within one immutable construction scope may reduce allocations without sharing mutable registry state, but no measured bottleneck or code-size win was established. This is lower priority than tooling duplication; do not add a global cache as a speculative simplification.
