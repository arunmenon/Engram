# Pack/engine implementation design review — 2026-10-07

**Verdict: ready with conditions.** The architecture is a workable basis for bounded contract prototyping and implementation planning. It is not yet a closed implementation specification or evidence that an unfamiliar pack will produce its intended artifacts. Keep the existing registry, source adapters, projector, subscriptions and evaluation mechanisms. Resolve the blocking contracts below before the affected runtime slices; no new orchestration service or general adapter-generation framework is needed.

The strongest parts of the proposal are explicit source normalization, owner-versus-subscriber separation, strict new-domain admission, whole-catalog coverage, applicability rather than universal worker processing, and separation of local/source evidence from real Spanner acceptance. These are proposed controls. Current code supplies useful generic mechanisms but still permits silent omissions, ambiguous duplicate outcomes, and schedule-dependent artifact values. “Compatible pack” must therefore mean a pack passing a versioned capability/semantic/runtime conformance contract, not merely one that loads.

## Reusable pack conformance contract

Require a compact, versioned conformance fixture bundle alongside each compatible pack. Use the same runner/format for PDLC, CRM and the unfamiliar pack; avoid separate validators or special-case names.

1. **Authoring/load:** exact owned event catalog and subscriber references, capability requirements, dependencies, bounded payload contracts, field/type/key checks, conditional/cardinality rules, property ownership, allowed link proposals and retrieval intents. Reject invalid declarations and unsupported required behavior. Record optional inert behavior visibly.
2. **Activation:** API and applicable workers agree on the supported immutable interpretation set; required consumers/providers exist or activation refuses the promised behavior. Register retention obligations before accepting work. Verify wrong/stale bundle and unloaded-owner outcomes.
3. **Source/admission:** each fixture identifies original source kind/hash/revision, binding revision and semantics; expected normalized envelope/payload, authenticated source, contract/bundle identifiers, stable IDs and per-input receipt. Include invalid, unsupported, no-op, partial storage and conflicting same-ID cases.
4. **Artifact expectations:** record initial graph plus exact expected delta: typed node IDs, create/update/remove/preserve fields, lifecycle outcome, stubs versus observed artifacts, typed edge identity/status/trust, asserting event and applied rule/revision. Record forbidden nodes/edges and intentional no-op reasons. Bound cardinality; do not use count-only assertions.
5. **Worker/extraction:** fixture declares required versus skipped consumers and persisted prerequisite/effect outcomes. Scripted model outputs test schema/proposal limits, invalid answers, partial writes and replay. Live model quality is a separate bounded evaluation and cannot guarantee exact generated content. Test A/B/A, missing references, restart, two replicas and all relevant worker orders.
6. **Retrieval:** fixture supplies question/intent, seeds/scope/session, exact supported answer and source evidence, excluded answers/edges, and complete versus unknown negative outcomes under truncation/deadline. If result ordering is intentionally free, compare a specified set; pagination order remains explicit.
7. **Upgrade/replay:** fixture pins original and target interpretations, expected diff/classification, legacy policy, subscriber/applicability change, available source documents/bundles, partial repair and rollback. Original ingestion replay and deliberate new mapping are different assertions.
8. **Spanner acceptance:** execute the same fixture through actual ingress, ledger, subscriptions, applicable workers and retrieval using Spanner for involved configured ports; preserve run ledger, source/diff/config fingerprints, limits/fault injection, exact observations and cleanup. Local conformance is a prerequisite, not cloud acceptance.

A useful unfamiliar fixture is a small `lab` pack with `lab.sample.received` and `lab.sample.updated`, a Sample composite identity `(facility, sample_id)`, declared reading units, optional nullable description, a bounded list of instrument references, one conditional link and an explicit subscription to another pack's event. Specify exact IDs such as `Sample:west|S-7` and `Instrument:west|I-2`, preserved/cleared description behavior, link-asserting events and a scoped “which instrument produced this sample reading?” answer. Run alone and combined, with mismatched lists, unsupported required capability, concurrent revisions and an unknown type. This is a proposed fixture, not an existing or executed pack. If extraction is optional, assert deterministic effects exactly and test proposals separately.

Static checks can establish declaration consistency and bounded supported syntax; they cannot establish source business meaning, approval authenticity, dynamic expression values, external candidate completeness, model truth, concurrency convergence, storage atomicity or native deadline behavior. Semantic fixtures cover chosen examples; runtime fault/concurrency/cloud tests establish only their bounded tested conditions. Neither is a universal proof over arbitrary future packs.

## Review prompt critique

The prompt is strong on pipeline boundaries, whole-pack coverage and avoiding false cloud claims. It correctly requires an unfamiliar pack and distinguishes source acquisition from execution. Retain it, with these refinements:

- Explicitly distinguish **idempotence from convergence**. Add A/B/A and two valid subscriber writes to one property; “retry/order cases” can otherwise focus only on FOLLOWS/CAUSED_BY.
- Require **same ID/different content** and **same source bytes/different binding revision**. “Same-ID retry” commonly tests identical input only.
- Ask for **missing versus null update semantics**, mismatched fan-out lengths and maximum generated write cardinality. Payload-size/schema bounds do not alone bound graph expansion.
- Define “exact source evidence” at claim/relationship granularity. Newest node provenance can satisfy a superficial provenance assertion while supporting the wrong claim.
- Require a concrete observation for **required worker disabled**, **subscriber added/removed**, and **accepted under N/processed under N−1**. Five consumers are today's topology, not a mandate that every future pack run all five.
- Bound “isolation”: type/namespace and session evidence isolation are in scope; tenant authorization is not proved by either. Document the deployment's authorization scope before promising multitenant pack isolation. Do not silently expand this into an app-wide security audit.
- Separate unsupported capability from accepted optional no-op, and distinguish global “pack complete” from each event's explicit supported/refused classification. The current matrix's generic oracle wording makes these easy to conflate.
- Ask for retained evidence behavior after source/document expiry or authorized deletion, within this pack provenance boundary. Protecting pending processing alone does not guarantee that a completed answer's cited source remains resolvable forever.

Residual limits: this source review did not exhaust every DSL expression or adapter, execute the tests, validate historical run artifacts, inspect remote issue updates, or independently verify provider specifications. Those are targeted implementation/conformance tasks, not grounds for a compatibility sign-off today.


## PE-01 public pack-write recheck — 2026-10-07

Later source grounding and registered diagnostic `runs/20261007-local-update-semantics-probe-01` correct one part of PE-01: public GraphOperations.upsert_nodes/upsert_edges call stored_values, which filters None; Neo4jPackGraph._props does likewise. The memory PackGraph diagnostic shows omitted and explicit-null values both preserve existing properties, while invalid int coercion silently preserves the old value. The lower-level apply_set can delete None fields but does not receive these pack None values. Spanner inherits the public filtering path; this diagnostic itself made no cloud calls. Keep PE-01 open for indistinguishable missing/null/invalid outcomes and deliberate clear support, without claiming omission deletion is reproduced. A/B/A old-value regression is independently reproduced and remains PE-02/#36 scope.
