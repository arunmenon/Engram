## Prioritized findings

**1. Blocking semantic decision: D04's reference-only target and rollback evidence cannot both use current observation provenance unchanged.** `docs/review/spanner-compatibility/2026-10-08-goal-07-event-coverage.md:105` requires null observation provenance before late fill. Every ordinary upsert automatically assigns source trust, updated_at and DERIVED_FROM (`src/context_graph/domain/pack_projection.py:474`–501). Artifact retrieval selects the newest DERIVED_FROM Event as observation provenance (`src/context_graph/retrieval/artifacts.py:1061`). Thus upserting a rollback target fabricates observation provenance immediately; explicitly adding DERIVED_FROM to an endpoint stub has the same retrieval defect. After fill, the later rollback timestamp would still win over the earlier deployment event.

Existing mechanisms can create an identity-only endpoint stub (`pack_projection.py:461`), then change its state using an explicit transition key (`domain/ontology.py:424`); worker order is nodes→states→edges. They cannot, with the currently declared relations/read policy, also preserve separately retrievable rollback evidence while meeting the null-observation promise. Smallest correction: freeze a bounded distinction between rollback declaration evidence and deployment observation evidence, including its HTTP representation, before implementation. A declared relation plus narrowly defined retrieval treatment is an option; do not disguise DERIVED_FROM as reference-only or create an invented successful deployment. Probe unknown rollback→HTTP null observation plus rollback evidence→late original deployment→HTTP real deployment observation plus retained rollback evidence/state. No broader framework is warranted.

**2. High: late fill needs a guarded success transition, and exact timestamps need canonical-equivalence fixtures.** `pdlc.pack.yaml:1347` transitions deployments to succeeded unconditionally; generic `state_change_applies` (`adapters/graph_ops.py:171`) checks only current state/only_from, not event time. Once a stub becomes rolled_back, a late deployed event currently undoes it. Freeze allowed predecessor states for deployed and upgraded (and explicitly decide deployment_failed behavior on the same identity); exclude rolled_back where required. Test both observed-target and unknown-target orderings. Require aware datetime admission for target_started_at; exercise Z, +00:00 and equivalent non-UTC offsets selecting the same canonical identity, plus neighboring timestamps selecting distinct attempts. Existing datetime key coercion supports UTC normalization (`domain/pack_projection.py:155`), so no bespoke identity scheme is needed.

**3. High false-pass risk: B05 “ledger-only” must assert absence of all domain output, not only Change.** `pdlc.pack.yaml:1318`–1324 uses an independently evaluated IMPLEMENTS target; an endpoint target may become a WorkItem stub even when the source Change key is missing (`domain/pack_projection.py:594`–596). A no-PR subject with a ticket token in subject/body can therefore create a reference artifact despite no Change or edge. Smallest correction: freeze B05 with ticket/reviewer text as a negative branch and either guard the whole mapping on a PR number or document its actual stub side effect; do not call such a case ledger-only. Keep B04's oracle tied to exact suffix regex, conventional-prefix result and Jira scope.

**4. Medium: reviewer text is an approval-valued artifact even without a review link.** `pdlc.pack.yaml:1321` assigns verdict approved, keys review_id from the entire reviewers-line capture and does not populate reviewer. B06 correctly forbids counting reviewed code, but its oracle should assert these exact properties, absent REVIEWS and unchanged Change lifecycle, and retrieve Review directly by ID. Include multiple names on one line to prevent assuming one authenticated review per person. Preserve this bounded limitation; no reviewer feature expansion is necessary.

**5. Medium: catalog no-write checks require settled baselines and independent expected identities.** Spec lines119–123 are sound but not an executable acceptance manifest. Local `tests/unit/test_pdlc_payload_contracts.py:30` hardcodes 24/4; its plan assertions do not prove HTTP/Spanner behavior. Freeze final 28 event types, independently authored IDs/properties/relations/evidence, exact validation variants and per-case disposition. For each duplicate/conflict/rejection, settle applicable workers before the baseline, submit one case, allow its relevant processing window, and compare all owned tables after; unrelated asynchronous mutation otherwise creates noise or obscures attribution. Mutate same-ID payload into another contract-valid value for conflict probes. Nested negative cases must first populate their containing optional object/list, so tests reach the intended field. Preserve failed runs rather than regenerate expectations from output.

## Bounded D04 recommendation

Prefer a pack-only DeploymentRollback node keyed by rollback Event ID, observed from that Event, with ROLLS_BACK→the exact Deployment stub. Transition Deployment via explicit target key (edge-target inference also works). No Deployment upsert or DERIVED_FROM is emitted by rollback. Add the action type to seeds and relation to intended traversal weights. Retrieval then presents rollback action evidence separately from null target observation. Late deployed upsert fills real observation provenance; create-only defaults preserve rolled_back and the success guard prevents regression. This is expressible with existing generic machinery after small pack declarations. Reusing core REFERENCES is less suitable: its current endpoint contract is Event→Entity and artifact traversal excludes Event provenance/session paths. Freeze the new action node and relation in D's oracle without adding an event type.
