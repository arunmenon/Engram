# Agent-assisted onboarding: implementation review

Reviewed 2026-11-04 on feature/engram-walkthrough, HEAD 27b4ba8, including the
current working tree. Scope: UI call paths, pack authoring, validation, review,
sandbox/approval gates, persistence/export and adjacent story authoring.
No product code, packs, expectations or runtime data changed. No live provider
call, fresh UI onboarding, Spanner test or deployment was performed for this review.

## Verdict

The current implementation is a constrained LLM-assisted authoring workflow,
not a coding-agent integration. ModelAuthor uses LiteLLM acompletion with JSON
output, engine feedback and up to three attempts. It exposes no tools, repository,
shell or workspace to the model. The server creates temporary YAML for validation;
that is not an agent editing files. Durable artifacts are JSON in the draft store;
pack/evaluation YAML is serialized by the export endpoint.

This is a useful foundation for declarative pack authoring. It is not yet a
complete general-domain agent that plans stories, creates fixtures, executes the
sandbox and independently iterates on semantic failures.

## Actual path

1. UI saves structured Content: scope, policy, specification/schema/sample text,
   existing packs, optional roots, decisions, questions and trust configuration.
2. POST author requires provider permission, redaction confirmation, scope and
   at least one source. One source kind is sufficient to begin; execution has
   stronger readiness requirements.
3. ModelAuthor supplies Proposal/Pack schemas, syntax example, sample statistics,
   operator content and available previous review/validation/evaluation feedback.
   It requests one complete JSON proposal, not a code patch.
4. Proposal contains a summary, cited/inferred facts, blocking questions, optional
   pack, limitations and tracked removals. Before executable inputs it can return
   a conceptual proposal with no pack.
5. The backend validates JSON, verifies exact source excerpts, validates Pack,
   composes selected packs, checks admission, plans sample projections and reports
   errors. Up to three calls may repair a pack within a 245-second author budget;
   each call has an 80-second timeout and 12,000-token output cap.
6. If the final proposal passes structural/source verification but engine checks
   still fail, it can be saved with limitations. This is not execution readiness:
   the API reruns validation and later gates block an invalid pack.
7. Operator answers are saved and marked pending; Apply answers makes another
   authoring request. Previous operator reviews/results are supplied when retained.
   Review resets after a new proposal. Sources changing clears prior author context.
8. Running examples requires reviewed facts, accepted pack/removals, identity and
   lifecycle decisions, schemas/samples, validation, reviewed questions, expected
   graph nodes and reviewed trust. The operator initiates the real sandbox run.
9. Approval requires passing current sandbox checks and hashes content, proposal,
   validation and sandbox result. Export emits pack YAML, evaluation YAML and record.
   Export is available before approval, so exported draft data is not proof of
   approval. Neither approval nor export activates a runtime.

## What creates which artifact?

| Artifact | Creator today |
|---|---|
| Customer sources and sample events | Operator input; not automatically generated by pack authoring |
| Pack JSON, summary, facts, questions to resolve | LLM proposal, checked by backend |
| Sample statistics, validation/planned deltas | Deterministic backend |
| Reviewed questions and expected answers | Content/operator input; pack author is told not to rewrite this oracle |
| Pack YAML / evaluation YAML | Server serialization of pack and reviewed questions |
| Sandbox graph and evaluation results | Engine and sandbox runner |
| Approval identity/history | Backend |
| PDLC story outline, events and expected checks | Separate LLM workflow, then operator review and runner |
| Python implementation, code patches, test modules, PR | Not created by the authoring model |

## Findings ordered by consequence

### 1. High: general-domain pack authoring does not connect to general-domain story authoring

journey_authoring.py reads fixtures/pdlc/pdlc.pack.yaml, uses frozen_registry,
references frozen-pdlc-pack and validates evaluations as pdlc. It is a useful
PDLC-only story workflow. Do not present it as generating tests for any newly
authored procurement, finance or incident pack. Pack authoring itself does not
produce the Content sample events or reviewed expected-answer artifact.

Next: pass the selected draft's validated registry/pack digest into a bounded story
workflow. Keep outline, generated events, expected results and human review separate.
Prove one non-PDLC story end to end before broader claims.

### 2. High: quotation existence is not semantic grounding

verify_proposal requires sourced facts to have quotes and verifies exact substring
membership. It does not prove the quote supports the claim, or map every executable
rule to a cited fact/operator decision. The operator basis has no enforced decision
reference. A valid quote plus an unsupported changed explanation passes the verifier
in an offline probe. This is not a prompt-injection exploit demonstration; it is a
limit of the grounding guarantee.

Next: attach rule/type/key paths to source/decision references, show unsupported
choices explicitly, and review semantic support. Do not replace human review with
another model's unqualified approval.

### 3. High: removal review is not a behavioral diff

changes.pack_items inventories node/edge names, properties, lifecycle state names,
event names and intent names. It does not compare keys, projection operations,
transition guards, payload requiredness or retrieval configuration. Offline probes
confirmed key edits and deletion of the actual projection section produce an empty
removal list. Separate engine checks may catch invalid edits; these probes do NOT
show that such a proposal would pass execution or approval. They show the removal
warning cannot explain all behavior changes. The workbench also classifies against
None, so its initial label supplies no before/after comparison.

Next: show a semantic before/after diff against the previous draft proposal, with
changes to identity, mapping, lifecycle, contracts and retrieval explicitly reviewed.

### 4. Medium: repair loop checks structure/sample planning, not full semantics

The author does not autonomously run sandbox evaluations. validate checks composition,
contracts/admission, intent availability and projection plans. The operator runs the
sandbox afterward and may request another revision using retained evaluation feedback.
This separation is deliberate and useful for preserving expected outcomes, but it
is not an autonomous generate-test-debug coding-agent loop.

Next: expose a bounded run-feedback-revise workflow after expectations are reviewed;
require the operator to review behavior changes and never silently change the oracle.

### 5. Medium: schema input and selected-pack context are limited

Schema uploads are JSON text; saving checks JSON parsing, not semantic validation
of an OpenAPI/JSON Schema contract or proof that generated contracts conform to it.
The author gets names of selected packs through Content, plus Pack schema and a
syntax example; the prompt does not explicitly supply the selected registry's full
definitions. Composition errors are discovered afterward by the real loader.

Next: send a compact engine-derived inventory of available types/interfaces/intents,
and check supported input contracts where feasible. Label samples as observations,
not proof of global uniqueness or requiredness. Existing prompt already warns this.

### 6. Medium: bounded execution is not a durable agent workspace

Authoring jobs run as in-process asyncio tasks, with two jobs maximum. SQLite stores
records and revision fences; restart recovery marks interrupted jobs rather than
resuming agent work. Inputs can contain up to 20 sources of 40,000 characters each;
there is no visible token-aware evidence selection in ModelAuthor. Prompt instructions
are not equivalent to a semantic enforcement mechanism, although absence of model
tools substantially limits what malicious source instructions can execute.

Next: retain useful attempt diagnostics and make interruption/retry explicit. Add
context budgeting before expanding document intake. A distributed agent service is
not necessary to address the immediate correctness gaps.

### 7. Medium: UX retains generic mandatory policy decisions

readiness always requires identity and lifecycle decisions. OperatorFlow synthesizes
these standing questions even outside the assistant's unresolved-question queue.
This can ask operators to answer lifecycle questions for domains without stateful
types. Review is required but not every question is domain-specific.

Next: derive required choices from the proposed pack, or support an explicit reviewed
not-applicable answer, with a concrete example of each decision's effect.

## Existing controls worth preserving

- Explicit provider permission and redaction confirmation before authoring.
- No model tools, credentials, shell or deployed-runtime access.
- Real engine checks rather than model assertions of success.
- Conceptual proposal distinguished from executable pack.
- Revision-fenced completion/cancellation and interrupted-job recovery.
- Pending answers must be applied before pack acceptance; removed data needs review.
- Expected answers remain outside the pack author's output schema.
- Sandbox gate before approval; old results invalidated after relevant edits.
- Owner-scoped storage, safe failure references, version preservation during repair.

## Recommendation

Call the current feature an assistant-guided pack author with engine validation.
It creates real artifacts, but it is not a coding agent. Fix semantic diff/grounding,
connect selected-pack story generation, then run one fresh UI onboarding with a
non-PDLC pack and reviewed failure cases. If later needed, give an agent a small set
of draft/validate/sandbox tools with bounded iterations. A general shell-enabled
coding agent is warranted for actual adapter or engine development, not simply
because a pack is serialized as YAML. Keep runtime changes in a separate engineering
workflow and never let the authoring agent change expectations just to pass tests.

## Implementation follow-up: revision review, confirmations and guidance

Implemented locally:
- Server-generated structural before/after pack comparison, covering keys,
  lifecycle definitions, event contracts/handling, projection rules, retrieval,
  processing and dependencies. Unchanged values are omitted; pack metadata
  version/description/owner does not create behavioral review noise. Lists remain
  grouped, with exact rule details available. This is a structural comparison,
  not a semantic-equivalence prover.
- Exact-change acknowledgements are required by both UI and API. A repeated
  unaccepted revision retains its original comparison baseline; retry cannot hide
  an unacknowledged change. Stale or invented acknowledgement IDs are rejected.
  Identity edits have a plain-language warning about combining separate records.
- Standing identity/lifecycle input questions are replaced with confirmations of
  the displayed pack. Existing recorded policies remain visible. Genuine assistant
  questions still need answers applied through authoring. Confirmation itself
  makes no model call and is reset with a new proposal.
- Structured expected-answer IDs and expected/forbidden graph IDs are omitted from
  ModelAuthor's provider payload. Prior evaluation feedback is reduced to scores,
  question IDs and error presence. The original oracle remains intact for sandbox
  testing. This does not redact IDs mentioned in source documents, free-text
  instructions or previous generated explanations; it is not a data-loss filter.
- Question UI instructs operators to establish the business answer from source
  material before choosing generated candidate entities. This is an improvement
  in guidance, not independent semantic verification or a separate business-oracle
  artifact. Stronger decision-to-rule/source linkage remains outstanding.
- Failed-run guidance distinguishes event-processing failures, stored-graph
  mismatches and answer-only failures. Answer failures lead first to question
  type/start/scope inspection without claiming a particular root cause. No expected
  answers are automatically changed.
