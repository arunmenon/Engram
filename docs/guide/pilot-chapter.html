20 · Controlled developer pilot

Can another team use Engram and trust the evidence?

These pages explain the pilot even if you open them directly. A tenant is an isolated customer/data boundary. Core supplies shared activity records; User adds personal-context extraction; Memory adds explicit Beliefs/Goals and time-grouped Episodes; PDLC adds product-development artifacts. Selecting a pack configures supported behavior, not a separately deployed worker.

The pilot checks whether developers can submit realistic activity, retrieve the right knowledge and inspect why it was returned. It also checks whether another developer can reproduce the process and add a journey.

First, a journey is a connected sequence of activity that changes what Engram knows. A probe checks a boundary, such as a retry or an unauthorized read. We have 49 candidate journeys and 18 shared probes. The final coverage map records each candidate separately; 67 entries are not 67 passing journeys.

Tenant A: personal context

Core + User + Memory

Coding help, learning, research, work journals and personal planning. Track preferences, attributed beliefs, explicit goals and session history.

User extraction is enabled; PDLC is absent.

Tenant B: development knowledge

Core + PDLC + Memory

Product requests, designs, code reviews, tests, releases, incidents and development memory. Keep revisions, outcomes and sources distinct.

PDLC rules are selected; an extraction profile determines which prose can reach the model and what it may propose. User extraction is absent.

The pilot uses real Spanner and actual configured models when judging extraction or summary quality. Scripted outputs can isolate regression behavior, but cannot establish real-model usefulness. Direct graph inserts and manual repair do not count as a successful journey.

Read the actual checkpoint evidence

P01–P11 have bounded engineering acceptance. P11 passed 69 checks from a pinned clean checkout, including a JSON-added story and tenant exclusion. P12 packages the coverage and team handoff. See the verification walkthrough for exact runs, retained failures and independent review, and the candidate coverage map for what remains partial or unsupported.

What the coverage verdicts mean

Full: the frozen shared probe met its declared checks. Partial: useful parts passed, but the whole catalog story or every requested read was not established together. Diagnostic: a check exposed an unsupported or unresolved behavior. External: a human/team or deployment step is still needed. These words describe evidence, not percentages or guarantees for every possible input.

What this does—and does not—claim

Success means the selected journeys meet declared expectations, isolation checks pass, failures are visible and reproduction works. Engram's read APIs return structured graph/context evidence; a downstream application's generated prose needs a separate evaluation.

Team/repository access policies within a tenant, vector-search/load benchmarks, historical-data migration, changing packs in a running runtime and general forced-crash recovery remain separate. Known limits stay visible beside the affected journey.

21 · Understand the experiment

A journey has a story and an independently declared result

A test case defines behavior to check; a test run is one execution. The commit ID identifies the code revision tested. The expected result below is written before execution so it can expose a defect instead of merely repeat what Engram returned.

Before sending data, we write down what should change, what should be retrievable and what must not happen. We do not derive the expected result from whatever Engram returns.

Illustrative expected fragment, not a live result. Each run points to the test it executes and its own source Event. Read “TestRun → EXECUTES → TestCase” as “this execution ran that test.” Read “TestRun → DERIVED_FROM → Event” as “this Event supplied the recorded result.” The direction labels show these source-to-target connections even where the line is drawn leftward.

What we require

The answer must preserve both outcomes, the commit and the exact supporting sources. A passing rerun must not overwrite the failed run. A coverage link says the test is intended to check a requirement. Only the particular run’s outcome says whether that execution passed, failed or was skipped.

Technical contract for every journey
  • Stable journey ID, purpose, selected tenant/packs and prerequisites.
  • Ordered full event envelopes and payloads with fixed identities/timestamps.
  • Expected accepted/rejected responses, stored identities, properties, edges and evidence.
  • Supported read endpoints, query bodies, limits and expected/forbidden results.
  • Applicable worker outputs, real-provider quality rubric and completion criteria.
  • Repeat instructions, retained-data policy and per-run evidence.

Current catalog entries are discovery templates. A runnable specification must freeze these details; a template is not an executable test.

22 · Tenant A — Core + User + Memory

Personal context changes over time—and belongs to someone

Attribution asks whose statement or preference this is. Scope asks where it applies: an owner, session or named context. For example, Alice’s short-answer preference during incident support must not replace Bob’s preference or Alice’s separate design-review style.

These 25 candidates vary the knowledge problem: context-specific preferences, attribution, ambiguity, recall, revised beliefs, explicit goals and incomplete evidence.

Start with the family, then select a journey. Each entry explains what goes in, what to ask and what must not be concluded. Prior representative verification is a starting point; it does not mean this new journey passed.

Several connected histories

A coding assistant and on-call helper, a learning coach, a research assistant, a work journal, and planning activities. Alice and Bob provide positive owner controls: retrieve each person’s actual data before checking that one person’s results exclude the other.

Keep meanings separate

Interest is not expertise. A belief is an attributed assertion. A completed Goal needs an explicit action. A late note can produce a new Episode membership snapshot while earlier snapshots remain; it must not rewrite their saved membership.

How to read technical labels

U means the common/User worker path; M adds explicit Memory actions; R means rejection with no new worker delivery. VR means prior representative verification; NP means fresh proof required; G means a capability gap; PD means a product decision. P0/P1/P2 are local priorities, not results. Source abbreviations are defined in the linked Tenant A catalog.

Finding an earlier session without its ID, selecting a preference for the current context and distinguishing two meanings of the same word all need fresh proof or an honest gap verdict. Explicit structured Memory actions cannot substitute for successful prose interpretation.

23 · Tenant B — Core + PDLC + Memory

Follow what was planned, built, checked, shipped and learned

A specification states intended product behavior; a requirement names a specific need. A high-level design (HLD) describes the approach; a low-level design (LLD) details a part of its implementation. Tickets track work, pull requests propose code changes, and releases and deployments record different delivery steps.

These 24 candidates use several development stories: an audit-export feature, hotfix and incident, library release, abandoned prototype and explicit engineering Memory.

PDLC means product development life cycle. An artifact is one of those domain objects. Its graph links a specific requirement, design or pull request to related records, rather than treating all text about a feature as the same object. The links must come from supported declarations or permitted model proposals; a plausible relationship is not enough.

Each stage has alternatives: a design can be replaced, a prototype abandoned, a test skipped, a release published without deploying, or a deployment rolled back. These differences are the reason for the diverse journeys.

How to read technical labels

G means graph projection; E means session extraction; N means enrichment; C means scheduled consolidation. X+ means matching PDLC prose extraction; X0 means no matching profile. The inventory covers all 28 declared PDLC event types, meaning the accepted kinds of activity message—not every possible journey or relationship. That does not promise every schema relationship has a producer. Model proposals are not confirmed operational facts; an incident after an upgrade does not establish causality.

24 · From input to retrievable knowledge

Five shared workers; different applicable work

Choose a tenant example, then a stage. A trigger is the condition that starts processing, such as session end or a timer. An applicable rule/profile is one selected by this bundle and input. The four teaching stages below organize the explanation; they are not four synchronized runtime barriers.

Packs select supported behavior. The workers are independent responsibilities, not five consecutive processing phases. Some act on each event; others wait for a session trigger, matching profile or schedule.

25 · Read the knowledge, not just the row

Finding an exact ID is only one kind of retrieval

An exact seed supplies the starting node ID. Lexical discovery finds words or domain keys in stored fields. A paraphrase asks the same question with different wording. Testing these separately tells us whether the system can find knowledge, not just return a record whose ID we already supplied.

We test precise traversal and useful discovery separately. Supplying the expected node ID must not hide a failure to find the same knowledge from the developer's wording.

Question typeExampleWhat we check
Exact identity and linksTrace this specific export requirement.Correct revision, connected designs/work/tests and source Events; no unrelated neighboring requirement included merely through a shared parent
Key/title discoveryShow the audit-export work.Relevant domain key/text candidates; unrelated export feature excluded
ParaphraseWhich change prevents unauthorized rows leaving the workspace?Useful evidence specified before the run, or an honest miss; supplying the expected ID afterward cannot rescue this discovery test
Current versus historyWhat does Alice prefer now, and what changed?Supported current state and revision evidence via the appropriate read contract
Time and sessionsWhat happened during yesterday's investigation?Correct temporal scope and available membership; explicit-session recall distinguished from automatic discovery
Unsupported premiseWho approved design v2 when only v1 has approval?No invented v2 approval; absence scoped to inspected evidence and read limits

Choose the read surface deliberately

GET /v1/context/{session_id} gives bounded session context. POST /v1/query/subgraph handles Event/entity and supported Memory/User intents. POST /v1/query/artifacts handles domain keys, text and permitted artifact traversal. Direct User reads currently require admin; the pilot must not grant broad admin just to obtain a pass.

Event/entity retrieval can use configured vector search. Artifact retrieval has no artifact-vector seed channel. A lexical hit is not evidence that vectors participated. A query limit bounds how many records or relationship steps can be read. Truncation means some candidates were omitted because a limit was reached; inspect it before declaring that knowledge is absent.

Reference: what belongs in each read record?

The exact request, endpoint/intent, seed mode, owner/session, budgets, expected and forbidden node/edge/source sets, actual response, truncation and actual search-channel evidence where required. Keep generated application answers separate from Engram's graph/context result.

26 · Judge what happened

A pass requires the right result and the right evidence

A probe changes one condition—such as retrying an Event or using the wrong tenant credential—to check a boundary. Forbidden effects are changes that must not occur. A deterministic fault check deliberately controls one failure or ordering condition; it does not measure real-model quality.

HTTP acceptance proves the event was accepted. Acknowledgement proves handling ended for a delivery. Neither alone proves the intended knowledge exists or is useful.

Stakeholder handoff

Each stage ends with expected/actual results, payloads and responses, worker and graph evidence, repeat instructions, retained failures, independent review, a demo and GitHub issue reconciliation. Partial coverage updates evidence; it does not close a broader umbrella.

27 · A suite other developers can use

What another developer needs to reproduce the pilot

A fixture is fixed test input with expected results. A runner sends it through the supported APIs and checks those expectations. To pin code, packs and model configuration means record the exact versions/settings so another developer can repeat the same experiment.

The team walkthrough publishes exact prerequisites and commands for the P11 reproduction. It uses a clean pinned checkout, one A Goal, one B Change, a JSON-added library Change and a cross-tenant exclusion. Existing dependencies may be reused only when declared; project imports must come from that checkout. Independent human repetition remains separate.

The deliverable is a reusable pilot suite—not a demonstration that depends on the author's machine or private setup knowledge.

Before execution

  1. Pin code, packs, provider model/configuration and required roles.
  2. Configure authorized databases and their binding/generation (owner/epoch). Document how each producer maps agent_id to a logical user; a tenant credential does not establish that mapping by itself.
  3. Preserve retained data; do not reset a shared target implicitly.
  4. Keep credentials outside tracked fixtures; record provider usage, consolidation timing and timeouts. The pilot has no artificial call-count or spend ceiling.
  5. Follow the documented public API and five-workers-per-tenant launch.
  6. Check accepted/processed/pending/failed visibility and supported read surfaces.

After execution

  1. Inspect per-journey expected versus actual and evidence.
  2. Separate deterministic regression results from real-provider quality.
  3. Retain original failures, inputs, responses and configuration.
  4. Have another developer reproduce a journey from each tenant and an isolation probe.
  5. Add one journey through the same format and helpers.
  6. Record undocumented intervention as a reproducibility defect.
