Start with what runs where

Who this guide is for: an engineer who knows basic HTTP requests and database rows, but is new to Engram. Start here for the overall model; use the page selector to revisit a component. Each worker lesson explains its input, trigger, output and limits.

Architecture guide with current Memory/tenant updates and a new controlled-pilot chapter.

Engram is the application. Spanner is its managed storage and query backend. A request reaches Engram first; Spanner does not interpret ontology packs or run Engram workers.

Engram turns recorded activity into connected knowledge that an application can retrieve with evidence. It stores source events and builds a graph that makes relationships easier to query. Configured retention controls how long source records remain available; durable storage does not mean unlimited history.

A ledger stores accepted activity records. A graph represents things as nodes and named connections as edges: for example, a test run EXECUTES a test case. Workers build those graph records from ledger input so retrieval can follow their connections.

The whole flow, before the details

Write request → accepted event in ledger → asynchronous workers → graph records → retrieval request → structured context.

“Asynchronous” means the write can finish before the workers finish. The ledger is the durable, retention-governed source history; the graph is a derived view of it.

A worker loop repeatedly receives activity and performs one processing job. A pack declares the types and supported rules that job can use. An LLM is a language model used on selected text-processing paths; an embedding represents text as numbers for similarity comparisons. Neither is needed for every graph write.

2 · Architecture fundamentals

Tables indexes and graph definition

Read this as a storage map. A graph node is one stored thing; its label identifies its type, such as Event or Requirement. Its properties are named values such as a title. An edge names a connection between two nodes. JSON is the key/value document format used for flexible properties.

Three different kinds of Spanner objects are involved. Tables store our records. Indexes provide additional ways to find those records. The property graph definition exposes node and edge tables for graph queries.

Delivery tables track work separately from the graph: a group names a job, a cursor records how far that group has received events, and a pending delivery records work it has not acknowledged. A shard is one polling partition. TenantControl stores a binding (tenant + database + configuration) and an epoch, a generation number used to reject stale runtimes.

How Engram talks to Spanner

An interface describes an operation Engram needs, such as “read an event.” An adapter implements it for a backend such as Spanner. Startup code—the composition root—connects the adapters to Google’s Python client library (SDK) and a database handle, the client-side object identifying the target database.

A transaction groups database operations into one committed change; it does not include the entire asynchronous workflow. A read snapshot supplies a consistent view, while a mutation inserts, updates or deletes records. The SDK reuses communication sessions through its session pool.

The write request ends at the ledger

Acceptance means Engram validated and durably recorded an input. A receipt is the response describing that outcome. Authentication identifies the caller; authorization decides what that caller may do. Both precede accepting input for a bound tenant.

The API validates and accepts an event. It does not synchronously run all five workers before returning the ingestion receipt.

Envelope

Shared fields such as event identity, event type, timestamp, session and agent/source context.

Payload

The domain-specific JSON object. Pack contracts define the fields required for supported event types.

Server acceptance identity

For a bound runtime, this records the authorized tenant/database/binding, selected configuration and engine revision. It also keeps a request fingerprint: a digest of normalized accepted content used to distinguish an unchanged retry from conflicting reuse of the same identity.

The caller cannot freely supply these server-owned authority fields.

Important outcomes: an identical accepted retry can return duplicate; conflicting reuse of its identity returns a conflict; invalid new input is rejected. Batch writes can span transaction-sized chunks, so inspect per-item outcomes rather than assume the entire large request was one atomic transaction (all items commit together or none do).

5 · Architecture fundamentals

What one ledger row represents

A consumer is a worker instance reading the ledger. The notification tells it which Event to load; the full payload stays in the Events row. A ledger position is an ordering key assigned at acceptance so consumers can find newer records.

An Events row is the durable record from which consumers load an accepted event. The delivery notification contains its identity; the worker loads the document separately.

Events row — simplified physical picture
event_id → primary key
document → normalized event envelope plus payload
acceptance → server-owned interpretation identity when bound
commit_ts + batch_index + event_id → ledger position
shard → calculated from session ID
summary / keywords / search_text → searchable derived fields
in_log / in_session_index / dedup_active → lifecycle flags

Source time

The event timestamp describes when the activity occurred at its source.

Ledger position

The Spanner commit timestamp records acceptance; a batch index distinguishes records within an accepted batch, and the event ID breaks remaining ties. Together they describe accepted ledger order. They are not the same as source time.

Shards divide polling work. The subscription defaults to 16 logical partitions. A repeatable hash calculation maps a session ID to one partition, keeping its delivery position in that shard. Each job has a cursor per shard: the last position it received, not the last position it successfully processed.

The ledger is not the graph. A row in Events does not itself create a GraphNodes row. Search/enrichment fields and retention flags can change; “ledger” does not mean every column remains immutable forever. The acceptance identity protects interpretation of accepted content.

Where E17 lives after acceptance

Its accepted document contains the tool event and content. A delivery notification can carry only its identity; a worker fetches the document when it needs the payload.

6 · Architecture fundamentals

How consumer groups actually run

The worker is running Engram code. The group is a named progress record. The subscription adapter connects them to the ledger. With this backend, the worker polls Spanner instead of consuming Redis Streams.

Polling means repeatedly asking for the next batch; a batch is a group of delivery notifications. ACK is acknowledgement that one group has finished handling a delivery. PDLC means product development life cycle: the optional pack for artifacts such as requirements, code changes and tests.

First: what is a worker, and why do we need five roles?

A worker is a running piece of Engram code that handles a particular job after an event is accepted. For example, saving “a test failed” is one job; creating a TestRun in the graph is another. Keeping these jobs separate lets a slow extraction job avoid blocking the initial write request.

The five names below describe jobs, not packs. They can handle activity from optional domain packs as well as the original agent-oriented use cases. A consumer group is each job’s durable progress record; it does not define what that job computes.

Distinguish the three pieces

Worker: an application loop that performs a job, such as graph projection. Engram starts the loop; Spanner does not execute it.

Consumer group: a name such as graph-projection, with durable cursors (positions already delivered) and pending records (deliveries not yet acknowledged). It is not a separately running database service.

Subscription adapter: Engram code implementing “read new”, “read pending”, “acknowledge” and “claim abandoned work” using Spanner transactions.

Workers may run in separate application processes. Test runners can host their ordinary loops together; the logical group boundary is independent of the process layout.

Groups versus consumers: consumers in the same group share its transactional delivery bookkeeping. Different groups independently receive the event for their own responsibilities. Do not infer a deployment-wide ordering between the five workers.

What happens after failure or restart

Before acknowledgement: a failure leaves the delivery pending. A crash after a graph write but before acknowledgement can cause that work to be delivered again. Writes therefore need retry-safe identities and behavior.

On startup: the worker ensures the group exists, claims eligible stale deliveries, drains its pending items, then enters the new-event loop.

Repeated failures: the pending-drain path tracks attempts and can explicitly move a repeatedly failing item to ConsumerDeadLetters.

Current limitation: ordinary main-loop processing failures are not guaranteed a live retry. The generic pending-drain call is at startup; some transient storage operations separately retry in place.

Spanner’s role is durable coordination and storage. Engram owns the loop, processing code, acknowledgement boundary and recovery policy. Group completion also does not prove every expected semantic output exists; the verification must inspect graph writes, evidence and retrieval.

What “dynamic” means here

The generic projector can interpret supported rules from a selected pack, and the pack-extraction worker can use that pack’s supported profiles. A new domain pack can reuse those mechanisms without custom wiring for every pack pair.

Session extraction, enrichment and consolidation still contain specialized implementations. A pack cannot invent a new worker capability by naming it in YAML. New behavior outside the engine’s supported contracts needs an implementation and verification first; an unsupported requested handler must fail validation.

Pack selection is assembled during startup or activation. It does not start worker processes, guarantee their providers are ready, or make every event produce all possible outputs.

Worker deep dive: graph projection

This lesson uses a separate test-result Event, T17; page 4’s E17 remains the Billing tool event. A TestCase names a test definition. A TestRun is one execution of that test, with its own outcome and identity.

Build the graph representation of accepted facts. This worker is deterministic: code applies declared field mappings, rather than asking a language model to decide the facts.

Why this worker exists

The ledger tells us that something happened, but a row of event JSON is awkward to follow as a network of connected facts. We need a graph that lets us move from a test result to its test, or from a review to its change.

Its job: Read the accepted event and apply explicit rules to build those graph records.

You should get: An Event that preserves the activity, plus any matching domain objects and links. The rules—not a model guess—decide what gets created.

By the end, you should be able to answer: How did this payload become these particular nodes and arrows?

Which graph schema does projection use?

Schema versus records: a schema defines allowed kinds of nodes, their identities/properties and relationship endpoints. The worker writes particular records using those definitions. It does not invent a new ontology each time it reads an event.

Where the schema comes from: at startup, Engram loads mandatory core plus selected compatible packs, validates their declarations and resolves supported capabilities. That checked configuration governs these writes. Spanner stores the records in GraphNodes and GraphEdges; EngramGraph exposes those tables as a graph. A type such as TestRun is not a separate Spanner table.

Now look inside the implementation

A delivery identifies an accepted event. Projection loads its document and plans the common Event plus applicable activity links. Selected domain packs can add deterministic rules for the same event. An artifact is a domain object such as a TestRun; it is separate from the Event recording that the result arrived.

Before and after: a failed test

Supplied: test identity, run identity, outcome = failure, commit SHA and any explicit change/requirement references in a valid finished-test payload.

PDLC rule: create TestCase and TestRun; connect TestRun → EXECUTES → TestCase. Add only applicable declared RAN_AGAINST / VERIFIES links.

After: core Event plus domain records. Failed is a test outcome, not a worker exception. An identity-only referenced node can be a placeholder; it is not proof that its own source event was received.

A scoped identity uses enough fields to distinguish records: repository + test ID separates two repositories’ tests named “expiry.” A commit SHA identifies a particular code revision; a reference to it must be supplied, not guessed from a test name.

How ontology packs compose

An ontology is the vocabulary and structure of allowed node types, properties and relationships. A pack combines those declarations with supported behavior. The loader reads and checks them; a bundle is the resulting combined configuration used by Engram.

First Engram assembles and checks the instructions. Then the API, workers and retrieval use those instructions. These are two different stages.

Composition is useful because one tenant may select Core + User while another selects Core + PDLC + Memory. A dependency names something a pack needs from another definition. A capability names behavior the engine already implements. Checking these prevents a declaration from requesting a missing type or unsupported handler.

Flow A — assemble the configuration at startup

What “combine” means

Core contributes Event, Entity and Summary. User requests specialized user extraction. Memory adds explicit Belief/Goal action producers and eligible Episode consolidation, with their types and evidence contracts. References between these definitions must resolve. Engram does not generate a new worker for every combination.

One service, two authorized tenant runtimes

A dispatcher routes a request to the tenant runtime allowed by its credentials. A credential grant pairs caller identity with its tenant and permitted roles. A child runtime is that tenant’s configured Engram API/storage context, not a new database chosen from the request body.

How the ownership guard rejects stale runtimes

This check is called fencing. A process from an older generation may still be running; guarded operations check the durable ownership tuple and refuse it instead of letting it write with stale authority.

An epoch is a runtime-generation number. An older or mismatched generation must be refused by guarded operations. A binding associates tenant, authorized database and checked pack bundle. Spanner stores records; it does not choose packs or run worker loops.

Failure boundaries remain important

ACK clears a group's pending delivery, not the ledger Event. Pending work can survive processing failure. Bounded cooperative stop/restart was verified; general live retry, forced termination and every maintenance operation were not. Do not draw recovery as unconditional self-healing.

Maintenance operations such as pruning history, replaying events or requesting reconsolidation remain unsupported in this tenant path, as do streaming import, unbound native webhooks, public cursors and global metrics. Finer team/repository policies within a tenant are separate design scope.

Earlier isolation checks used fixed, scripted external-model output to hold extraction behavior constant. They establish a bounded routing/data boundary, not real-model quality or a complete hosted service. The pilot must establish usable setup and realistic simultaneous activity separately.

What another developer needs to reproduce the pilot

A fixture is fixed test input with expected results. A runner sends it through the supported APIs and checks those expectations. To pin code, packs and model configuration means record the exact versions/settings so another developer can repeat the same experiment.

The team walkthrough publishes exact prerequisites and commands for the P11 reproduction. It uses a clean pinned checkout, one A Goal, one B Change, a JSON-added library Change and a cross-tenant exclusion. Existing dependencies may be reused only when declared; project imports must come from that checkout. Independent human repetition remains separate.

The deliverable is a reusable pilot suite—not a demonstration that depends on the author's machine or private setup knowledge.
