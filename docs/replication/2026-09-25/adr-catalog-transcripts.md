## ADR-0007

This ADR gives the Redis and Neo4j design a cognitive model. It is a useful vocabulary for assigning responsibilities, but it should be understood as an engineering analogy rather than a claim that the system reproduces a biological brain. Five memory types are named: sensory memory is the transient request body before validation; working memory is the bounded context assembled for a specific request; episodic memory is the immutable Redis event ledger; semantic memory is the derived Neo4j graph; procedural memory represents learned workflows and reusable action patterns in a graph substructure. Only four tiers are persistent design responsibilities: sensory memory is implicit and lasts less than a second; working memory is constructed on demand and discarded after use. Episodic and semantic memory are the two principal stores. Procedural memory was initially future work and later gained workflow, then behavioral pattern concepts through the personalization ADR. Working memory must be capacity-bounded. The default maximum is 100 nodes and three graph hops. Results are ranked by recency, importance, and query relevance, with later amendments adding user affinity. Related events may be grouped into episodes. Every returned item uses the Atlas response and carries provenance. Episodic memory stores detailed, instance-specific events. Each event is captured once under an idempotent identity, ordered by Redis stream position, and associated with session, trace, agent, parent, and tool context. This is the authoritative history and the basis for deterministic replay. Semantic memory stores the relational interpretation, entities, causal links, temporal links, summaries, embeddings, importance, and access history. These properties can evolve. Retrieval may reinforce a graph node by updating access count, last access time, and stability, while the source event remains unchanged. Procedural memory extracts repeated, successful sequences into an experiential hierarchy. A raw case can be abstracted into a strategy and then into a reusable skill. This is intentionally downstream; evidence of workflow should remain traceable to concrete event sequences. The life cycle is not a single straight line from short-term to long-term. Ingest and first preserves the episode. Asynchronous consumers project and enrich it. Retrieval then assembles a small working set from the episodic and semantic representations. Periodic consolidation discovers higher-level knowledge and may prune low-value graph detail. The code mapping is Redis as rapid episodic encoding, Neo4j as gradually consolidated semantic structure, and workers as the transfer process. The advantages are clear component ownership and a vocabulary for future features. Risks include conceptual overreach, noisy importance scores, and blurred tier boundaries. For external replication, label every stateful feature with its tier. Raw immutable events belong to episodic storage. Mutable scores and relationships belong to semantic projection. Per-request context belongs to working memory. Reusable action patterns belong to procedural memory. If the same datum is copied across tiers, document which copy is authoritative and how the others are rebuilt. This simple exercise prevents accidental mutation of source history. End of ADR zero zero zero seven,

## ADR-0008

ADR zero zero zero eight: memory consolidation, decay, and active forgetting. Status: accepted. This decision turns the graph from an ever-growing mirror of events into a maintained memory system. The guiding idea is that forgetting is necessary for useful retrieval, but forgetting the graph must not silently rewrite the event history. The pipeline has three stages. Stage one is continuous structural projection. It creates event nodes, follows edges from session order, and caused-by edges from parent identifiers. Stage two, Asynchronous, enriches nodes with keywords, embeddings, summaries, and computed importance. It may add similar-to edges above a configured cosine threshold and references edges for extracted entities. Stage three periodically revisits older graph regions, discovers cross-session relations, generates hierarchical summaries, updates importance from graph structure, and prunes low-value detail. Ranking combines recency, importance, relevance, and user affinity. Recency follows an exponential curve based on the time since occurrence or last access. Stability increases when a node is successfully recalled, causing that node to decay more slowly. Importance is normalized from a 100 graph score. Relevance comes from semantic similarity and has a neutral fallback when embeddings are unavailable. User affinity acts as a smaller contextual booster based on session proximity, prior retrieval, and entity overlap. Stability growth is sublinear. This prevents frequently accessed nodes from becoming immortal. All weights, base stability, and boost parameters are runtime configurable. Retrieval updates occur on Neo4j properties, never by mutating the Redis source event. Graph retention has hot, warm, cold, and archive phases. In the first day, all graph detail remains. During the following week, weak similarity edges may be pruned. From roughly one week to 30 days, only sufficiently important or frequently accessed event nodes remain, with summaries replacing pruned clusters. Beyond the graph archive boundary, event nodes leave Neo4j while summary structure survives. Redis has a separate life cycle. Its stream and JSON retention windows are not the same as Neo4j's graph tiers. A record can disappear from one representation while remaining in the other. Later life cycle work adds archive before delete, so raw events can survive outside Redis. Keep these two-tier systems separate in configuration and mental models. Consolidation can run on a timer, by manual trigger, or when recent accumulated importance crosses a reflection threshold. Concurrent runs are locked. Summaries prefer a language model when available and fall back to deterministic text when it is not. Pruning must protect active causal chains and create summaries before deleting detailed clusters. The risks are tuning error and irreversible information loss. Aggressive decay can hide rare but critical facts. Weak decay allows graph volume and retrieval noise to grow. Summary quality can also remove nuance. Metrics therefore track lag, last consolidation, graph size by tier, pruned nodes, reflection triggers, and score distributions. For external replication, start with conservative retention, then make every threshold configurable. Keep a reproducible source archive. Build tests proving that retrieval reinforces graph metadata without changing source events. Summaries retain links to evidence, and rerunning consolidation is idempotent. Measure retrieval miss rate before tightening pruning. High fidelity means matching the life cycle invariants, not deleting data at exactly the same wall clock age in every environment. End of ADR zero zero zero eight.

## ADR-0009

ADR 0009: Multi-graph schema and intent-aware retrieval for agent memory. Status: Accepted. This ADR defines how one shared property graph supports several kinds of reasoning without creating separate databases for each view. The foundational node types are event, entity, and summary. Event nodes represent projected source events and carry identifiers, timestamps, session and trace context plus derived enrichment. Entity nodes provide identity across events and sessions. Summary nodes compress an episode, session, or agent-level body of evidence while retaining links to the underlying material. Later amendments expand the complete schema to 11 node types by adding personalization, belief, goal, and episode concepts. The initial relationships form orthogonal semantic views. follows is the temporal backbone and answers when. caused by expresses direct or inferred causal dependency and answers why. similar to expresses embedding-based association and answers related questions. references connects events to durable entities and supports who or what. summarizes creates a hierarchy that can be browsed from abstraction down to evidence. Later ADRs extend the schema to 20 total edge types. intent-aware retrieval gives these relationships different weights. A why query prioritizes causal edges. A when query prioritizes temporal edges. A what query emphasizes references. A related query emphasizes semantic similarity. General queries begin balanced. Personalization later adds who is, how does, and personalize intents. The caller may provide an override, but the system normally infers multiple intents from query text and conversational context. The system also selects seed nodes. It extracts entities from the query, locates recent and important context around the current session and agent, and may include the user's graph neighborhood. Multiple intent traversals run in parallel and are merged. Nodes supported by more than one intent receive multi-signal confirmation. Proactive nodes can bring back a previous resolution or important entity connection that the literal query did not request, but those nodes must be labeled as proactive. Modern amendments make retrieval hybrid. graph, vector, and lexical channels run together. Reciprocal rank fusion combines their ordered results without requiring comparable raw scores. Personalized pagerank can add structural importance. Maximal marginal relevance balances relevance against redundancy. Hypothetical document expansion and language model intent classification are optional and time-bounded with deterministic fallbacks. Traversal is always bounded by depth, node count, neighbor count, and timeout. Embeddings live on Neo4j nodes, avoiding a mandatory third vector database. Similarity edges use high thresholds and pruning to prevent edge explosion. Entity resolution uses exact matching plus reviewable same as and related to links. Transitive clusters choose a canonical identity without destructively merging uncertain entities. Every result includes provenance and scoring. This lets callers see not just the graph node, but the readies event and the reasons that affected ranking. Schema changes are deployed by updating projection logic and rebuilding Neo4j from the event source. For external replication, preserve tight nodes and relationships, the intent matrix, bounded traversal, hybrid channel fusion, provenance fields, and the distinction between direct and proactive results. Create golden query fixtures for why, when, what, related, and personalization questions. Compare returned node sets, edges, scores, intents, seeds, and provenance, not merely final text. Also preserve tenant isolation when choosing node keys. A globally unique-looking identifier is not a substitute for an explicit tenant boundary. End of ADR 0009.

## ADR-0010

ADR 00010: Redis as event store. Status: Accepted. This ADR supersedes the earlier Postgre event store plan and establishes the current storage foundation. Redis Stack provides streams for ordered delivery, Redis JSON for complete documents, and Redis Search for indexed queries. The data model uses several coordinated keys: a tenant-scoped global stream receives every event in order, a per-session stream supports efficient session reads, one JSON document stores the complete event, a sorted set records recently seen event identifiers for idempotence. A Lua script updates these structures atomically on ingestion. The script checks the deduplication set, a new event is appended to the global and session streams, written as JSON, batched at the global position path with the generated stream identifier, and added to the dedup set. A duplicate produces no side effects. Batch ingestion pipelines multiple script invocations into one network round trip while each event retains individual atomicity. Consumer groups turn the global stream into a worker coordination mechanism. Projection, session extraction, enrichment, and consolidation can advance independently. Acknowledgment occurs after successful side effects. The pending entry list supports crash recovery, automatic claiming recovers work from dead consumers, and poison messages move to dead-letter streams after bounded retries. Redis JSON and Redis Search serve secondary queries by session, agent, trace, event type, tool, importance, text, and time. Stream entry identifiers provide hot replay order. Once old stream entries have been trimmed, a full cold replay can page through indexed JSON documents in occurrence order or restore archived files depending on lifecycle configuration. Durability is a conscious trade-off. The default combines snapshots with append-only file persistence synchronized every second. That allows a possible one-second loss window in a crash. Replication with a wait command improves acknowledgment guarantees, while append-fsync always is available when stronger durability is worth lower throughput. The no-eviction memory policy ensures Redis rejects writes rather than silently deleting source events. The event lifecycle distinguishes hot streams plus young data from colder JSON-only data. Community deployments have a retention ceiling, and ADR 0014 adds archive before delete to prevent permanent loss. Stream trimming is pending entry list safe, session streams are keyed after retention, and dedup identifiers are removed after their protection window. Schema validation occurs in strict pedantic models because Redis has no foreign keys or column constraints. Credentials use secret-aware settings. Clients treat durable position as an opaque string. The event store interface stays behind a port so future scale phases can introduce Kafka while preserving the application contract. For external replication, use Redis Stack rather than plain Redis because JSON and Search are a part of the contract. Verify the key prefix includes the tenant consistently in both rights and index definitions. Configure persistence and no-eviction explicitly. Exercise atomic duplicate submission, consumer crash recovery, dead letters, safe trimming, indexed cold reads, and archive restore. The most important fidelity test is that a successful API acknowledgement corresponds to a recoverable source event under the durability policy you advertise. End of ADR 0010.

## ADR-0014

ADR 0014, archival and lifecycle management, status: accepted. This ADR closes production gaps that would otherwise cause silent data loss, unbounded Redis growth, corrupt JSON, or a consolidation worker that never runs. The first decision is archive before delete. Expired Redis JSON events are exported as compressed JSON lines files partitioned by date. Development can use a file system adapter. Production can use object storage through the archive store port. The ordering is strict: query expired events, write the archive, verify success, and only then delete from Redis. A failed archive write stops deletion. Second, consolidation schedules itself. An in-process asynchronous timer starts the maintenance cycle at the configured interval, with six hours as the documented default. Manual stream triggers remain available. A lock prevents overlapping runs. This is sufficient for a dedicated single consolidation process, but multiple replicas require external leadership or distributed locking to avoid duplicate timers. Third, the global stream can have an approximate maximum length, and periodic trimming respects consumer progress. Pending entry list, say, trimming finds the oldest unprocessed position across projection, extraction, enrichment, and consolidation groups. The trim cutoff cannot advance beyond that position. Fourth, completed session streams are deleted after their retention window. The worker scans session stream keys, reads the newest entry, and removes streams older than the threshold. Fifth, the event deduplication sorted set is cleaned during each maintenance cycle, so one identifier per event does not accumulate forever. Sixth, the ingestion Lua script no longer modifies serialized JSON using a regular expression. It reads the document and then sets global position at an explicit JSON path while staying inside one atomic script. This avoids corrupting nested payload text that happens to contain the same field name. Seventh, batch ingestion is optimized. The original amendment described concurrent calls with a semaphore. The effective later implementation uses a Redis pipeline so many script calls share one network round trip. Each event is still atomically inserted or deduplicated. Graph lifecycle also removes orphan nodes after event deletion, except for long-lived profile anchors and intended summary survivors. Neo4j derived properties are not archived because they can be recomputed. The source event archive is the recovery artifact. The lifecycle progresses from full Redis and Neo4j detail, through stream trimming and graph edge pruning, to summary replacement object or archival, and eventual cold storage. Exact ages are configuration policy. The critical invariant is that raw source data reaches a recoverable archive before its last Redis copy disappears. For external replication, implement and test the failure boundaries. Simulate archive success followed by delete failure and verify the next cycle is idempotent. Simulate archive failure and prove no deletion occurs. Hold the message pending while trimming. Run two consolidation triggers together, create orphan candidates, and verify only eligible types are removed. Restore an archive and replay it. Also add explicit leadership if you deploy more than one consolidation worker. The local lock protects only one process. End of ADR 0014.

## ADR-0016

ADR 0016, security architecture, status: accepted. Anchor stores sensitive agent traces and user-derived knowledge. This ADR establishes the minimum API security boundary for multi-tenant deployment. Authentication uses two bearer token guards. The standard API key protects ordinary version one endpoints. The admin key protects administrative and GDPR operations. Tokens are compared in constant time to avoid timing leakage. If a key is absent, its guard is disabled for development. That convenience is also a production hazard. Deployment validation must fail closed when a production environment lacks either required key. Rate limiting uses an in-process token bucket with a standard tier and a smaller admin tier. Health metrics, documentation, and schema endpoints are exempt. Every normal response exposes remaining and reset information, while exhausting returns the appropriate retry guidance. Because state is local to one process, adding API replicas multiplies the effective allowance. Production systems that scale horizontally need a gateway or shared distributed limiter. CORS origins are configurable and default broadly for development. Credentials are disabled by default. Production must replace wildcard origins with an explicit allow list and expose only required methods and headers. Input is validated at the API boundary with strict pedantic models. Event types follow the dot-separated namespace. Identifiers have explicit formats. Graph queries have hard maximums for nodes and depth. The SDK adds a second client-side validation layer for path traversal, invisible Unicode, encoded sequences, payload sizes, pagination, and retry behavior. Secrets use protected configuration types and must never appear in module dumps, logs, exceptions, or representation strings. This includes API and admin keys as well as Redis and Neo4j passwords. Transport and MCP errors are sanitized because those messages are likely to enter logs, dashboards, or model context. This short ADR does not by itself implement full authorization. Authentication proves possession of a key. Tenant isolation still depends on consistently propagating and filtering tenant identity in Redis keys, Neo4j node identities, queries, archives, and metrics. External replication should make that distinction explicit. For external replication, create separate development and production profiles. Production startup should require non-empty standard and admin keys, encrypted transport, restricted CORS, secret injection outside source control, and a shared rate limiter when multiple processes serve traffic. Add negative tests for missing, malformed, swapped, and timing-sensitive credentials, cross-tenant identifiers, oversized requests, traversal parameters, and sanitized error messages. Security fidelity is proven by denied behavior, not by the presence of middleware classes. End of ADR 0016.

## ADR-0017

ADR 0017: Observability architecture, status: accepted. This decision defines how operators determine whether NRAM is healthy, fast-cached, and recoverable across an asynchronous pipeline. Prometheus metrics cover four areas: HTTP counters and latency histograms describe request volume, endpoints, status, and duration. Ingestion metrics count events and batch sizes. Consumer metrics count processed messages, errors, dead letters, and lag by group. Graph query histograms measure Neo4j latency by query type. Rate limit counters reveal rejected requests. The metrics endpoint is publicly scrapable within the deployment network and exempt from normal authentication and rate limiting. Structured logging uses structlog with key-value context rather than unstructured text. Log level is configurable. Worker logs name the consumer, message identity, outcome, error, retry, or dead letter action, and consolidation cycle state. Machine-readable fields make filtering and alerting reliable. Request correlation begins with the X-request ID header. The service accepts a safe incoming identifier or generates a version 4 UUID, binds it to logging context, and returns it to the caller. Each response also includes processing time. The identifier should be forwarded into downstream work or event metadata when end-to-end correlation is required. Otherwise, API and worker traces remain only partially connected. Health has two levels: a basic unauthenticated endpoint answers whether the process is alive. A detailed admin endpoint checks Redis, Neo4j, graph statistics, and stream length. Readiness should fail when required dependencies cannot support traffic, while liveness should avoid causing restarts for a recoverable downstream outage. Consumer observability is particularly important because successful ingestion does not mean the graph is current. Operators need pending counts, oldest pending age, last successful processing time, dead letter growth, and consolidation duration. One recorded gap is that the consumer lag gauge was defined before every path populated it, and external implementation should verify emitted samples rather than assuming a metric name guarantees data. Metrics are in process, so process restarts reset counters unless Prometheus retains scraped history. Labels must remain low cardinality. Use root templates and consumer names, not event user, session, or tenant identifiers. Logs can carry detailed identifiers under access and retention controls. For external replication, build a small operational dashboard around API latency and errors, ingestion rate, consumer lag, dead letters, graph query latency, Redis memory, Neo4j capacity, and last consolidation success. Create alerts for sustained lag, repeated dead letters, archive failure, memory pressure, and missing worker heartbeats. Send one synthetic event through ingestion, verify that its request identifier or trace can be followed to projection. Observability fidelity means an operator can distinguish API health from pipeline freshness within minutes. End of ADR 0017.

## ADR-0001

ADR 0001: Traceability First Context Graph. Status: Accepted and amended. This is the product-level architectural anchor for Ngram. Begin with the problem Ngram is trying to solve. Agent systems can usually tell us that an answer was produced, but they struggle to explain what happened, why it happened, and which source facts led to it. Existing observability products record traces for human debugging. Ngram makes a different promise: context returned to an agent carries provenance that the agent or an auditor can follow back to its source. The decision is therefore traceability first, not generic memory first. Five commitments define that phrase: agent and tool actions are captured as append-only events; retries are safe through idempotent ingestion; causal lineage is represented by parent event identifiers; every context response includes provenance pointers; the semantic graph can be rebuilt deterministically from ordered source events. The original design also required personal information to be separated through forgettable payloads, although the current repository explicitly defers that mechanism and uses graph-side cascade deletion as the available GDPR path. The architecture deliberately separates the immutable record of what happened from the derived representation of what it means. The current effective implementation uses Redis as the event source of truth and Neo4j as the graph projection. That is an important amendment. Early text in this ADR discusses a Postgres-only first phase and an eventual Postgres plus Neo4j system. ADR 0001 supersedes that storage choice. Do not reproduce the historical Postgres design when replicating this snapshot. Ordering is represented by a Redis stream entry identifier called global position. Treat that value as an opaque cursor. Given the same ordered event history and projection version, the graph should be reproducible. This rebuild property is what makes schema evolution recovery and auditing practical. The retrieval contract is equally important. Context is never just an untraceable block of text. A returned node identifies its event session, agent trace, timestamp, source store, and global position. Queries are bounded by depth, node count, and timeout, so a graph traversal cannot expand without limit. The ADR aligns the system with OpenTelemetry and W3C provenance concepts, but the alignment is conceptual. Operational edge names such as caused by, follows references, similar to, and summarizes are chosen for graph retrieval. Later ADRs refine the exact mapping. There are real costs: a source ledger plus a derived graph creates eventual consistency, projection lag, replay requirements, and more operational components. The bet is that those costs are justified because provenance becomes essential when agents move from demonstrations into consequential production workflows. For external replication, preserve the invariant rather than every original technology choice. First, keep an immutable, idempotent event contract. Second, preserve stable causal and session identifiers. Third, provide a total replay order. Fourth, keep semantic state derived and rebuildable. Fifth, return provenance with every retrieved context item. If your external platform cannot satisfy all five, it may reproduce the user interface, but it has not reproduced Ngram's defining architecture. End of ADR 0001.

## ADR-0002

ADR 0002: Service Stack is Python plus FastAPI. Status: Accepted and amended. This decision establishes the application runtime, and more importantly, the boundary between framework code and domain logic. Ngram is implemented in Python 12 with FastAPI and Pydantic. Python was selected because the surrounding agent language model embedding and data processing ecosystems are strongest there. FastAPI provides asynchronous request handling, typed endpoint contracts, generated OpenAPI documentation, and fast iteration. Pydantic provides strict validation at the API boundary, which becomes especially important because Redis does not enforce a relational schema. The decision is not permission to let FastAPI spread through every layer. Business rules must stay framework agnostic: event models, scoring, pagination, re-ranking, intent logic, contradiction handling, and extraction validation belong in domain modules. Interfaces to Redis, Neo4j, archival storage, graph maintenance, and model providers are expressed as ports. FastAPI routes adapt HTTP input to those domain contracts. This separation lets tests use protocol-conforming stubs and lets an external replica replace infrastructure without rewriting its core behavior. The compute model changed as the architecture matured. A normal web service is mostly input-output bound. Ngram also performs embedding generation, entity extraction, summarization, graph enrichment, and periodic consolidation. These tasks must not block the API event loop. The effective deployment therefore separates the API process from worker processes: projection for structural graph writes, extraction for session knowledge, enrichment for embeddings and metadata, and consolidation for periodic summaries and lifecycle maintenance. Redis adoption also amended the dependency profile. The original Postgres driver and migration tooling are no longer part of the event store path. The service uses asynchronous Redis access, while Neo4j remains the graph adapter. Machine learning dependencies should be isolated in the enrichment worker or delegated to a hosted service, so the API image can remain lean. The positive consequence is a productive, typed ecosystem with a natural fit for agent integrations. The negative consequence is that Python needs process separation and careful asynchronous discipline for CPU-heavy work. It also creates a risk of framework lock-in if route models and infrastructure clients leak into the domain. For external replication, match four things: use Python 12 and FastAPI if high fidelity is the priority, preserve strict Pydantic validation, keep domain code independent of FastAPI, Redis, and Neo4j clients, run CPU- or model-heavy work outside the API process. If your environment requires another web framework, treat it as a replaceable adapter and keep the same event code and response contracts. End of ADR 0002.

## ADR-0003

ADR 0003: Dual store with Redis source of truth and Neo4j projection. Status: Accepted and amended. This ADR answers a foundational storage question. Ngram needs two very different capabilities: a durable, ordered record of events and fast relationship-oriented traversal. One representation is not asked to optimize both jobs. The effective dual store is Redis plus Neo4j. Some original paragraphs still say Postgres, but ADR 0001 supersedes those references. Redis is the operational source of truth for episodic events. Neo4j contains a query-optimized semantic projection. The projection is derived, eventually consistent, and disposable. If it is corrupted, lost, or changed by a new schema, it is rebuilt by replaying source events. The cognitive interpretation introduced later is useful: Redis behaves like fast episodic encoding, detailed, time-ordered, and instance-specific. Neo4j behaves like semantic memory, relational, consolidated, and optimized for multi-hop reasoning. The projection workers implement systems consolidation between the two. This design prevents a critical category error: a Neo4j node is not automatically the authoritative business record. Properties such as importance, access count, summaries, embeddings, and similarity links may change as enrichment evolves. The original event identity, timestamp, agent session, trace, payload reference, and global position remain anchored in Redis. A query result combines graph utility with source provenance. The consistency model is asynchronous, an accepted event can exist in Redis before it appears in Neo4j. Consumers acknowledge messages only after successful graph writes. Clients and operators must understand projection lag. Ngram does not promise a distributed transaction across both stores. The advantages are efficient traversal, immutable event history, and recovery through replay. The costs are another data store, more integration tests, lag monitoring, and dual-store failure modes. Credentials are represented with secret-aware configuration types, and Neo4j indexes include session identifiers because session scope retrieval is a dominant path. For external replication, maintain an explicit authority map: Redis owns source events and replay order, Neo4j owns derived graph structure and query acceleration, worker checkpoints or consumer group state own delivery progress. Never allow a graph-only mutation to become an unrecoverable source fact. Test the architecture by deleting a disposable Neo4j database, replaying events, and comparing the rebuilt structural graph. Also test the opposite failure: when Neo4j is unavailable, event ingestion should remain safe and projection should recover later.

## ADR-0004

ADR 004: Immutable event ledger with idempotent ingestion. Status: accepted and amended. Agents, clients, and networks retry. Events can arrive twice, arrive late, or be presented after a partial failure. This ADR makes duplicate delivery normal rather than exceptional. Every event has a stable event identifier and an immutable envelope. Core fields include event type, occurrence time, session identifier, agent identifier, trace identifier, payload reference, and the system-assigned global position. Optional fields include tool name, parent event identifier, completion time, status, schema version, and an importance hint from 1 to 10. The importance hint is not the final importance score. It records the producer's opinion at ingestion time. Enrichment computes the authoritative graph-side score later. The current storage implementation is Redis, not the Postgre design described in the original decision paragraph. A Lua script performs the critical write atomically. It checks a sorted deduplication set for the event identifier. If the identifier is new, the script appends to the tenant's global stream, appends to the session stream, writes the complete Redis JSON document, records the return stream identifier as global position, and inserts the event identifier into the deduplication set. If the identifier already exists, the script returns a duplicate result without partial side effects. The global position is a Redis stream identifier, such as a millisecond timestamp followed by a sequence. It is represented as a string and must be treated as opaque by clients. Its purpose is ordering and replay, not user-facing arithmetic. Validation occurs through strict pedantic models before the Redis operation. This is weaker defense in depth than relational constraints. So malformed envelope tests are part of the contract. The ledger remains append-only. Derived keywords, embeddings, summaries, access counters, and computed importance belong to Neo4j and are not edits to the event. Idempotence has its own lifecycle requirement. The deduplication sorted set cannot grow forever. A maintenance cycle removes old identifiers after the configured dedup window. That creates a deliberate time boundary for retry protection and must be aligned with producer retry behavior. Batch ingestion uses Redis pipelining to reduce network round trips while preserving atomicity for each individual event. A failed batch can therefore contain a mixture of new and duplicate results, and callers must inspect the typeed response rather than assuming an all-or-nothing relational transaction. For external replication, copy the event contract first, preserve immutable identifiers, strict validation, atomic deduplication, and an opaque replay cursor, and tests for simultaneous submissions of the same identifier, a crash around the write, malformed fields, duplicate batch members, and replay ordering. Do not update an existing event to make a retry succeed. A retry must return the prior identity or an explicit duplicate outcome without changing history. End of ADR 004.

## ADR-0005

ADR 005: Asynchronous projection worker with replay support. Status: accepted and amended. This decision explains how Enram moves from ordered events to a useful graph without placing Neo4j on the ingestion critical path. The projection worker consumes Redis stream entries through a consumer group. For each event, it creates or merges the corresponding graph node, creates temporal follows relationships inside a session, and creates caused by relationships from parent event identifiers. Graph writes are idempotent, so redelivery is safe. Messages are acknowledged only after the graph write succeeds, giving at least once delivery with idempotent effects. The worker must be restart-safe, expose lag, and support complete replay. Redis consumer groups track normal progress. Their pending entry list records delivered but unacknowledged messages. On startup, workers use automatic claiming to recover messages abandoned by crashed consumers. A message that repeatedly fails beyond the configured retry count is moved to a dead letter stream with its original stream entry identifier, group, consumer, and delivery count. Operators can inspect and deliberately replay those entries. Microbatching improves throughput. The projection consumer buffers up to roughly 50 events or 100 milliseconds, then sends a batch graph write. Acknowledgement is deferred until the entire Neo4j batch succeeds. If the process crashes first, the buffered entries remain pending and can be processed again. A bounded least recently used cache remembers the last event for active sessions and is cleared when a session end event arrives. Replay is different from normal pending message recovery. Replay reconstructs Neo4j from the source event history, usually after graph loss, schema evolution, or projection code changes. Stage one replay restores the structural backbone, but it does not recreate every derived property. Enrichment and consolidation must run after structural replay to restore embeddings, summaries, similarity links, importance, and pruned hierarchy. Stream trimming must respect every consumer group's progress before deleting old stream entries. The maintenance path compares the age cutoff with the oldest unprocessed position across projection, extraction, enrichment, and consolidation groups. The effective trim point cannot move beyond an unprocessed entry. Without this safeguard, an entry could disappear while still pending, and recovery would become impossible. Workers depend on graph port protocols rather than route code or raw infrastructure wherever the repository has completed that migration. This keeps projection logic testable and allows external graph adapters. For external replication, test five failure scenarios: kill a worker after delivery but before graph commit, kill it after graph commit but before acknowledgement, send a permanently invalid message and verify dead letter handling, rebuild an empty graph from source events, finally trim a stream while one consumer group is deliberately behind and prove its pending entries survive. Passing these tests matters more than matching worker class names. End of ADR 005.

## ADR-0006

ADR 006: Context query and lineage API. Status: accepted and amended. This ADR defines Enram's public value surface. Ingestion records what happened. The query API turns that record into bounded, explainable context. The core endpoints ingest one event or a batch, retrieve ranked context for a session, query a subgraph, and traverse a node's lineage. Entity retrieval, administrative reconsolidation, feedback, user data operations, and other capabilities extend that base. The important contract is the Atlas response. Nodes, edges, provenance, scores, pagination, and metadata are returned together. Session context is working memory assembly. It ranks events with recency, computed importance, relevance, and optional user affinity. It is bounded by node count and depth and supports cursor pagination. The context endpoint is session scoped and does not require the caller to understand graph traversal. Subgraph querying is the richer retrieval path. ADR zero zero two eight, GDPR crypto shred and suppression list. Status: Accepted with production key management gate still open. Enrums immutable ledger creates a privacy tension. Audit and replay benefit from append-only events, but a data subject can require personal payloads to become irrecoverable. Deleting a Neo4j node is not sufficient because source events, indexes, backups, dead letters, or derived memories may still contain the information.
