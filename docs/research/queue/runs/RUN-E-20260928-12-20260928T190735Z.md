## What was done (engineering, not a run)
- Harness commit `004f652b0d1a1b326c2a4aa88723210ff673c684`, package `harness/memdec/`.
- `memdec.export`: reads Engram extraction output (one `SessionExtractionResult` per line, the shape `worker/extraction.py` produces), session transcripts and a session-to-repository map; emits store/skip candidates rendered as `{transcript_excerpt, item, quote}` (the same state shape the naming-audit templates consume; render version and renderer sha256 recorded) and supersession candidate pairs built from same-repository, same-preference-key items in time order (the rule `worker/extraction.py` already applies when it marks a preference superseded); assigns whole repositories to train/val/test with a seeded shuffle and the spec's minimum counts (10/2/8), writes per-record sha256 into `manifest.json`.
- `memdec.targets`: soft targets as the mean of available labels, 0.9/0.1 smoothing for single-labelled items (recorded per row), test-split targets written to a separate file so training and threshold fitting never open them, repository-overlap check across splits.
- Finding for the dataset owner: Engram has no Jev write gate yet, so there is no "logged write-gate candidate" stream. The exporter uses the extraction worker's preference items, which is the population a gate would see. If a different population is intended the spec needs to say so.
