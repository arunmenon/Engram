claim: For typing items from connected engineering tools onto the ontology's shared types and properties, a bind-time mapping per source field (small encoder retrieves the top 5 shared properties, a typed Choice picks one, a person confirms once; items are then typed by lookup) is no more than 3 points of type accuracy below a serve-time typed Choice per item, and at least 1 point above it or at least 50 ms p95 cheaper at serve time once unbound fields fall back to serve-time typing; a schema change (two renamed Jira custom fields) does not silently mistype more than 5% of items when the binding carries a breaking-change check. Sources: N-SURVEY-20260928-24 (Magneto, arXiv 2412.08194, VLDB 2025: an MPNet retriever fine-tuned on LLM-generated matches reached 0.860 +/- 0.088 MRR on GDC against 0.731 zero-shot, with COMA++ about 0.35 read from a figure; LLM-only schema-to-ontology mapping, arXiv 2609.13776, fell from 0.79 at 23 classes to 0.51 at 300; a column type annotator lost about 5 points on an unseen serialisation, arXiv 2512.22742), N-SURVEY-20260928-17 and N-SURVEY-20260928-18 (Palantir and Fabric IQ type data through a binding made once per source), N-SURVEY-20260928-26 (the survey synthesis recommending G7 move to bind time). None of these sources is on engineering tools and no typed decision model is in any comparison; the register holds no belief on source typing, so this decides G7's design rather than a grade.

arms (same 300 served items, same gold labels, same ontology version):
- A: serve-time G7: a Jev Choice per item per key field over the fixed tag sets, pinned version, neutral option names per E-20260928-06's frozen template.
- B: bind-time mapping: for each source field, a small encoder (MPNet-class, pinned) embeds the field name, description and 5 sample values and retrieves the top 5 shared properties; a Jev Choice picks one of the 5 (or "none"); one engineer confirms or corrects each mapping once, with minutes logged; served items are then typed by lookup. Fields mapped to "none" stay unbound and are untyped under B.
- C: B, plus arm A's serve-time Choice applied only to unbound fields.
- Schema change (applied after the main run): rename two Jira custom fields in the source export; re-run B and C with and without a migration rule (unknown field name or changed field id triggers a binding-breaking flag and routes the field to serve-time typing until re-confirmed).

metric: type accuracy on served items (primary: item's key fields mapped to the gold type and property); serve-time p95 latency and cost per 1,000 items; one-off binding effort (engineer minutes per source); after the schema change, silent mistype rate (items typed wrongly with no flag) with and without the migration rule.

predeclared margin: C (and B) at most 3 points below A; A within 1 point of C and C's serve-time p95 saving under 50 ms means bindings are not worth their upkeep; silent mistype rate after the schema change at most 5% under B with the migration rule (the card's margins).

sample size and power note: 300 served items from three backends (Jira, one GitHub repository, one Confluence space), 100 per backend, gold type and property for each key field labelled blind by two people. Under B every item from one source field shares the field's mapping, so the effective sample for B and C is the number of distinct source fields, not items; the build therefore requires at least 40 distinct key fields per backend (at least 120 fields), and intervals are cluster-bootstrapped by source field. At 120 fields and a paired discordance rate of about 0.10, the field-level SE of the accuracy difference is about sqrt(0.10 / 120) = 0.029, so the 95% half-width is about 5.7 points: the 3-point rule is decided on the point estimate with the interval reported, and results within one half-width of a margin are labelled inconclusive. The latency comparison is well powered (B is a lookup; A is a model call per item).

kill criterion: B and C both more than 3 points of type accuracy below A: keep G7 at serve time. A within 1 point of C and C saves under 50 ms p95: keep serve-time only. Silent mistype rate above 5% under B after the schema change without the migration rule: the binding needs a breaking-change check before it ships (reported as a required design change, not a kill of bind-time typing, if the migration rule brings it to 5% or below). Invalid (rerun, not a verdict): labeller kappa on type below 0.7, or fewer than 30 distinct key fields in any backend.

what a pass unlocks: the one gateway change the survey recommends, the ontology as a versioned per-backend contract with G7 at bind time (priority 3), a retriever in front of the typed Choice once the type set grows, and a breaking-change rule for bindings; the binding registry's design input for components 15 and 17.

cost (runs, tokens, people-days): labelling 300 items' key fields by two people, about 3 labeller-days; binding confirmation, under 1 engineer-day for 120 fields (logged as the arm's upkeep cost); arm A's Jev calls on 300 items x key fields; B's retriever on one CPU or GPU; exports and schema-change replay 2 engineer-days; harness 3 engineer-days. Cost M.

## Execution packet

- harness: harness not yet built: it must (1) export 100 items per backend from one Jira project, one GitHub repository and one Confluence space at a fixed timestamp, with field names, ids, descriptions and sample values; (2) load the frozen ontology version (shared types and properties); (3) run A per item and key field; (4) run B's retriever and Choice per source field, log the engineer's confirm or correct decision and minutes, and type items by lookup; (5) run C; (6) apply the schema change (rename two Jira custom fields) to the export and re-run B and C with and without the migration rule; (7) time serve-time typing per item; (8) write the manifest.
- dataset: BIND-TYPE-300: 300 items (100 per backend) with at least 120 distinct key fields, gold type and property per key field, labelled blind by two people and adjudicated; plus the schema-changed export. Frozen as Parquet with per-item sha256, backend, field ids, export timestamp and ontology version hash. Sending item text to a hosted vendor (arm A, B's Choice) requires the CTO to list the dataset in policy.md permitted_datasets; nothing runs until then.
- baseline arm: A, the serve-time Jev Choice per item per key field over the fixed tag sets, pinned version and template.
- metric definition and statistic: type accuracy = key fields mapped to the gold type and property / key fields; paired differences C minus A and B minus A with a 95% cluster bootstrap (10,000 resamples), clustering unit: source field; serve-time p95 latency per item; silent mistype rate = items mistyped with no breaking flag / items after the schema change.
- budget: policy unset (policy.md status: unset; sized M above).
- kill rule (machine-checkable): `valid = kappa >= 0.7 and min(fields_per_backend) >= 30`; `bind_ok = (acc["C"] >= acc["A"] - 0.03) or (acc["B"] >= acc["A"] - 0.03)`; `not_worth = (abs(acc["A"] - acc["C"]) <= 0.01 and (p95_ms["A"] - p95_ms["C"]) < 50)`; `needs_break_check = silent_mistype["B_no_rule"] > 0.05`; if not valid: verdict = "invalid"; elif not bind_ok or not_worth: verdict = "negative"; else: verdict = {"result": "positive", "breaking_change_check_required": needs_break_check, "rule_sufficient": silent_mistype["B_rule"] <= 0.05}.
- expected output manifest: `run_manifest.json` (backends, export timestamps, ontology version hash, model pins, template sha256s, migration rule sha256); `items.parquet` and `labels.csv` (both labellers, adjudicated, kappa); `bindings.csv` (field, retrieved top 5, Choice, engineer decision, minutes); `decisions.jsonl` (item, field, arm, type, property, latency, cost); `schema_change.csv` (item, arm, rule on or off, typed, flagged, correct); `metrics.csv` (per arm: accuracy, intervals, p95 latency, cost per 1,000, binding minutes, silent mistype rates); `verdict.json`; `receipts.sha256`.
