claim: On long-horizon terminal and coding tasks at a fixed 16K compaction threshold, deterministic verbatim truncation (CliffCompaction rules) resolves no fewer tasks than LLM summarisation compaction, within a 10-point non-inferiority margin, at no higher dollar cost per attempt; and a sliding window does not beat truncation by a clustered interval excluding zero.

arms (one frozen model, one frozen harness, threshold 16K tokens, same tasks, paired seeds):
- Arm A (baseline): harness-native LLM summarisation compaction.
- Arm B: CliffCompaction proxy at commit b48d660 with default rules (tool results over 500 characters dropped, those up to 500 kept verbatim, tool calls reduced to signatures, thoughts cut to 300 characters, system prompt and task kept, last K turn pairs kept, previous compactions discarded).
- Arm C: sliding window (system prompt and task prefix plus the most recent turns that fit under the threshold).
- In every arm the request body actually sent to the model is logged (the proxy rewrites requests invisibly to the agent, so without this what the model saw differs from what the harness logged).

metric: primary: task resolve rate (official Terminal-Bench 2.0 checker, mean over 3 attempts per task). Co-primary: dollar cost per attempt at a fixed, dated price list, cached and uncached input priced separately. Secondary: number of compactions per attempt; input tokens; wall-clock time; per-arm share of attempts that hit the turn cap.

predeclared margin: truncation_default if ci95_low(resolve_B minus resolve_A) >= -0.10 and ci95_high(cost_B / cost_A) <= 1.0, and not (ci95_low(resolve_C minus resolve_B) > 0). summaries_kept if ci95_high(resolve_B minus resolve_A) < 0, or if (resolve_C minus resolve_B) > 0.03 with ci95_low(resolve_C minus resolve_B) > 0. Otherwise inconclusive. The card's 2-point and 3-point thresholds were point-estimate rules; they are replaced by interval rules because at 60 tasks a 2-point difference cannot be resolved (see power note).

sample size and power note: 60 tasks x 3 attempts; unit is the task, clustering unit is the task (tasks are independent Terminal-Bench items; attempts are averaged). With a per-task SD of the paired difference of about 0.30, the SE is about 0.039 and the 95% interval half-width about 0.076. Power to show non-inferiority at a 10-point margin when the true difference is 0 is about 70%; at a 5-point margin it would be about 25%, which is why 10 is used. In the source, Table 6 differences between methods at 16K on SWE-bench Verified were within about 2.5 points (sliding window 72.80, CliffCompaction 71.33, summarisation 70.27), so this design can detect a large loss, not a small one, and says so. The cost endpoint is well powered: the source reports 21% vs 23% savings against full context for truncation and summarisation, and per-task cost ratios are tight.

kill criterion: truncation-only compaction is killed as a default if resolve_B is below resolve_A with ci95_high < 0, or if the sliding window beats truncation by more than 3 points with ci95_low > 0. Stop before running (not a result) if fewer than 60 tasks cross 16K in the pilot, any arm fails to log the request body actually sent, the proxy commit differs from b48d660, any pin is missing, or the executor model is also used to write the summaries in arm A under a different pin than the one declared.

what a pass unlocks: the in-session compaction default for our engineering agents (truncation that can be replayed from the ledger, or summarisation); whether summaries are ever a read surface; the first in-house on/off number that bears on B5, in its in-session form. Together with E-20260928-02 it answers whether dropped large outputs need a handle back to the ledger.
