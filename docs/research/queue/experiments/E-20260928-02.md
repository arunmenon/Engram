claim: Replacing tool observations over 10 KiB with a stable ledger handle plus a 1 KB excerpt after their first two provider requests, with exact bytes retrievable by handle, cuts input tokens per task by at least 20% on our frozen coding-agent task set, and every served excerpt and fetched chunk resolves byte-identical to the ledger. Task success is a guardrail, not a claim: this design can show harm, it cannot show non-inferiority.

arms (same frozen harness, model and version, same tasks, paired seeds):
- Arm A (baseline): full observations kept in context (current behaviour).
- Arm B (ObservationPack-style): observations of 10 KiB or more are sent in full for two provider requests, then replaced by `{handle, first 1 KB excerpt}`; a `fetch(handle, offset, length)` tool returns exact bytes from the ledger. Threshold and excerpt size fixed as in the source; not tuned on this set.

metric: primary: total input tokens per task (cached and uncached reported separately; primary uses total), B relative to A. Guardrail: oracle pass rate per task (mean over 3 rollouts). Secondary: number of fetch(handle) calls and bytes fetched per task; share of tasks where the mechanism triggered (any observation of 10 KiB or more); replay fidelity (share of served excerpts and fetched chunks whose sha256 matches the ledger bytes at that offset); cost per task at a fixed price list.

predeclared margin: tokens: handles_pay requires the ratio of mean input tokens B/A <= 0.80 with the 95% upper bound <= 0.90, and fidelity == 1.0. Success guardrail: handles_pay is blocked if the point estimate of pass_B minus pass_A is below -0.02 or its 95% lower bound is below -0.10. These thresholds are stated as a harm screen; "no significant harm" here is not non-inferiority, and the outcome text says so.

sample size and power note: 60 tasks, 3 rollouts each; unit is the task, clustering unit is the task (one task per sequence, so no further clustering). The token effect is large in the source (ObservationPack cut tokens on Opus 5 from 2.37B to 1.44B, about 39%, but only from 2.15B to 2.02B, about 6%, on GPT-5.6 Sol), so whether our saving reaches 20% is a real question that depends on the backend; per-task token ratios are tight, so the token endpoint is measured precisely if the mechanism triggers on at least a third of tasks. The success guardrail is weak: with a per-task SD of the paired difference of about 0.25, the SE is about 0.032, so the 95% lower bound sits roughly 6 points below the point estimate; a true 2-point loss cannot be distinguished from 0. This is the exploration slot: cheap and directional.

kill criterion: the claim is killed if the token ratio B/A is above 0.90 (saving under 10%), if fidelity is below 1.0 (a served excerpt that does not resolve to the ledger is a receipt defect), or if the success guardrail blocks. Stop before running (not a result) if fewer than 20 of the 60 tasks trigger the mechanism in a pilot of arm A on a separate seed (then the set does not exercise the claim), any pin is missing, or the fetch tool cannot address ledger bytes by handle.

what a pass unlocks: a costed, replayable context-assembly rule for large tool outputs (a served pointer to an immutable record, the R1 receipt pattern, used for R3 budgeting); a first in-house token number for handle serving; a direct input to E-20260928-03's truncation arm, which drops large outputs without a way back.
