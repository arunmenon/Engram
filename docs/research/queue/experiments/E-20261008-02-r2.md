claim: On memory gate requests from our own pipeline (write-gate Noul `quote_supports_item` and Choice `source_type`, recall-gate Noul), a frozen-encoder student fitted to Jev's probability distributions, with a kNN out-of-distribution gate and a fixed-sequence threshold chosen by a Clopper-Pearson rule at target 98% agreement, routes at least 40% of held-out gate REQUESTS entirely locally (no Jev call, no text egress for that request) while the share of all held-out requests whose local gate ACTION differs from Jev's stays at or under 2% on at least 18 of 20 descriptive splits; the same cascade with a point-estimate threshold violates the budget on more splits. Source: N-20261008-01 (Jevstiller README at f5f52e7, single author, not executed by us): at target 98%, held-out coverage 69.0 to 80.2% on three many-class short-text tasks and 22.2 to 24.1% on two noisy tasks, with the bound rule exceeding the budget on 1 of 100 splits versus 6 to 12 of 20 per task for the point estimate. The README's guarantee assumes an IID held-out calibration set; ours is clustered by project and time, so here the bound is an IID-only heuristic and the split counts are descriptive, not a 95% guarantee. Agreement with Jev is not accuracy.

Dataset deviation from the card, stated: the card asks for recorded production decisions; no dogfood tenant is named under POLICY-v1.1, so the log is built by running pinned Jev on gate inputs our extractor and recall path produce over permitted data (seeded T1 PDLC history, LongMemEval-S). The verdict says so.

Score `strength` (write gate) is not distilled. A write-gate request is therefore only "local" if strength is also not needed: the primary request-level metric counts a write-gate request as saved only when the request's local answers make strength unnecessary (item rejected locally by `quote_supports_item`); otherwise it still calls Jev and is NOT counted as saved, even if other questions were answered locally.

arms:
- A (baseline): every request goes to Jev (pinned version, pinned templates); the student is not consulted. Saved requests 0%, action disagreement 0% by definition.
- B: per-question cascade (frozen bge-small, logistic head on Jev soft labels, kNN OOD gate) with fixed-sequence bound threshold (algorithm below), combined per request: a request is answered locally only if every question it needs passes its gate; otherwise the whole request goes to Jev. 2% of requests are drawn into an audit slice before routing and always go to Jev.
- C: identical to B except each question's threshold is the loosest grid point whose point-estimate disagreement on calibration is at or under the same per-question allocation.

Threshold algorithm (both arms, per question): grid t = 0.99, 0.98, ..., 0.50 scanned in that order (strictest first). Allocation: the 2% request-level budget is split equally across the k questions a request type uses (Bonferroni: 2%/k per question, k = 2 write gate, 1 recall gate). B: at each t, compute the Clopper-Pearson 95% upper bound on (local and action differs from Jev)/(all calibration rows) for that question; continue while the bound is at or under the allocation; STOP at the first t where it is not, and retain the last passing t. If t = 0.99 already fails, the question has no local route (always Jev). C: retain the loosest t in the grid with point estimate at or under allocation (full scan, no stopping). This is fixed-sequence testing, so B needs no multiplicity correction across grid points.

Fitting details: logistic head, L2 C = 1.0, max_iter 1000, no early stopping (no validation split needed); encoder frozen. kNN OOD gate: k = 10 on the fitting set with self excluded when scoring fitting rows; cut = 99th percentile of fitting-row mean neighbour distance. A question with fewer than 1,500 fitting rows in a split gets no local route in that split (always Jev) and is reported descriptively.

Gate action, not argmax: for each question the action is what our gate does with the answer (accept/reject the item, chosen source_type, recall include/exclude). H5 acceptance uses a probability floor, so the student's action uses the same floor applied to the student's calibrated probability (temperature-scaled on calibration rows); the confidence_floor the README requires is therefore the H5 floor, and disagreement is counted on actions, not argmax.

metric (primary, request level): saved_rate = requests answered fully locally / all held-out requests (audit requests included in the denominator and counted as not saved); action_disagreement = requests answered locally whose any-question action differs from Jev / all held-out requests (any-question union, not per-question). Text egress = 1 minus saved_rate, reported. Secondary: per-question coverage and per-question disagreement, same denominator; violations = splits with action_disagreement > 0.02. Required downstream (not optional): write-gate F1 against H5 labels on the 90 H5 items and recall@5 on the P3 memory eval set, A versus B, plus expected calibration error of B's probabilities versus Jev on the locally answered rows. Statistic: 20 splits (fit 2,000 / calibrate 1,000 / hold out 2,000 requests), formed by grouped assignment where whole source projects (PDLC) and whole sessions (LongMemEval) go to one partition, and calibration and hold-out are drawn from strictly later time windows than fitting; seeds 0 to 19. Splits are descriptive: report median, range and count of violations; no binomial interval over split counts is computed. Inference on the pooled hold-out uses a cluster bootstrap (resampling source projects or sessions, 10,000 resamples, seed 7) for a 95% CI on saved_rate and action_disagreement.

predeclared margin: B passes if median saved_rate >= 40%, at most 2 of 20 splits have action_disagreement above 2%, the cluster-bootstrap upper 95% bound on pooled action_disagreement is at or under 3%, and the downstream checks are within the kill margins. Bound-versus-point contrast counts if C has at least 3 more violating splits than B (descriptive).

sample size and power note: at 2,000 held-out requests, a 2% rate has null SE about 0.31 points if requests were independent; a true 2.6% rate is about 1.9 SE above 2.0% and is NOT reliably distinguished from it, and clustering widens this further. This spec therefore does not claim to resolve 2.0 from 2.6; it claims to detect a disagreement rate of 3.5% or more (about 4.8 independent SE, with headroom for a design effect up to about 2.5) and uses the cluster bootstrap upper bound for the pass rule. Splits overlap in data and are a stability description, not replications.

kill criterion: median saved_rate of B below 25%, or B violates 2% on more than 4 of 20 splits, or cluster-bootstrap upper bound on pooled action_disagreement above 4%, or recall@5 with B more than 1 point below A, or H5 write-gate F1 with B more than 2 points below A.

what a pass unlocks: a measured, request-level agreement contract (saved requests, text egress, action disagreement) for keeping most gate text in-house with CPU-only serving, conditional on a shadow-deployment spec; B14 local evidence limited to: on our gate questions under project/time-clustered splits, a fixed-sequence bound threshold violated the budget on fewer splits than a point estimate (heuristic, not a guarantee). B13 evidence is limited to: downstream F1 and recall@5 on the routed population did not degrade beyond margin; no claim about escalation accuracy beyond that.
