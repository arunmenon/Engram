claim: Replacing tool observations of 10 KiB or more with a stable ledger handle plus a source-form excerpt (complete head lines and complete tail lines, together at most 1,024 bytes, with the byte offsets of both ranges and the original size) after their first two provider requests, with exact bytes retrievable by handle, cuts input tokens per task by at least 20% on our frozen coding-agent task set, and every served excerpt range and fetched chunk resolves byte-identical to the ledger. Status: exploratory. Task success is a harm screen, not a claim: this design can show harm, it cannot show non-inferiority, and a pass does not license adoption as the default.

arms (same frozen harness, model and version, same tasks, paired seeds):
- Arm A (baseline): full observations kept in context for the whole task (current behaviour).
- Arm B (ObservationPack-style, head and tail): an observation of 10,240 bytes or more is sent in full in the first two provider requests that contain it; from the third such request on it is replaced by `{handle, size_bytes, head: {offset: 0, length: h, text}, tail: {offset: size_bytes - t, length: t, text}}`, where head is the longest run of complete lines from byte 0 with h <= 512 and tail is the longest run of complete lines ending at the last byte with t <= 512; if the first or last line alone exceeds 512 bytes, that range is cut at the last UTF-8 boundary at or below 512 bytes and flagged `partial_line: true`. If head and tail would overlap, the tail starts at byte h. A `fetch(handle, offset, length)` tool returns exact ledger bytes. The head-and-tail form and the original size follow the source method (-full.txt line 125, per REV-20260928-04); the 10 KiB threshold and two-request window are as in the card and E-20260928-02; the 1,024-byte budget and the 512/512 split are our pins (the card's 1 KB), because the source text available to us gives no byte size for the excerpt. Nothing is tuned on this set.

metric: primary: total input tokens per task (cached and uncached reported separately; primary uses total), B relative to A, as a ratio of means. Guardrail: oracle pass rate per task (mean over 3 rollouts). Secondary: rewrite events per task (actual replacements of an observation by its handle in a provider request); fetch(handle) calls and bytes fetched per task; share of tasks with at least one rewrite event in the scored runs; replay fidelity (share of served head ranges, tail ranges and fetched chunks whose sha256 matches the ledger bytes at that offset and length); cost per task at the pinned price list; results restricted to the pilot-eligible tasks as a secondary cut.

predeclared margin: tokens: handles_pay_shadow requires fidelity == 1.0, the ratio of mean input tokens B/A <= 0.80, and its 95% upper bound <= 0.90. Success guardrail (harm screen): handles_pay_shadow is blocked if the point estimate of pass_B minus pass_A is below -0.02 or its 95% lower bound is below -0.10. The card's adoption margin (success within 2 points, with an interval) is not tested here; see the power note for why it cannot be met on this set.

sample size and power note: 60 tasks, 3 rollouts each; unit and clustering unit are the task (one task per sequence, so no further clustering; rollouts are nested in tasks and averaged per task before any statistic).
- Token endpoint (ratio of means R = mean_B / mean_A over per-task rollout means). Delta method: Var(ln R) is about (1/n)(CV_A^2 + CV_B^2 - 2 rho CV_A CV_B), where CV is the between-task SD over the mean of per-task tokens in each arm and rho is the across-arm correlation of per-task tokens. For a point estimate at 0.80 to have its upper bound at or below 0.90 we need 1.96 SE(ln R) <= ln(0.90/0.80) = 0.1178, so SE(ln R) <= 0.0601, so the bracket term must be <= 60 x 0.0601^2 = 0.217. No per-task token variance is available (REV-20260928-04 not_verified), so the following is illustrative, not measured: with CV_A = CV_B = 1.0 and rho = 0.9 the term is 0.20, SE = sqrt(0.20/60) = 0.0577, half-width 0.113, and a point of 0.80 gives an upper bound of 0.80 x e^0.113 = 0.896 (just passes); with rho = 0.8 the term is 0.40, SE = 0.0816, and the upper bound is 0.80 x e^0.160 = 0.939 (fails). Power at SE = 0.0577: 80% power for the upper-bound condition needs ln R_true <= ln 0.90 - (1.96 + 0.84) x 0.0577 = -0.267, so R_true <= 0.766; for the point condition, R_true <= 0.80 x e^(-0.84 x 0.0577) = 0.762. So this design reliably passes only if the true saving is about 24% or more; at a true saving of exactly 20% it passes about half the time. Because variance is unknown, the pilot (both arms, separate seed) measures SE(ln R) by task bootstrap and the run stops (not a result) if it exceeds 0.0601; the pilot uses one rollout per task, so its SE is conservative relative to the scored 3-rollout means.
- Success guardrail. With the original spec's assumed per-task SD of the paired difference of 0.25 (an assumption, not a measurement), SE = 0.25 / sqrt(60) = 0.0323 and the 95% half-width is 0.063. The screen blocks on the point rule with probability P(d_hat < -0.02) = Phi(-0.02 / 0.0323) = Phi(-0.62) = 0.27 when the true difference is 0 (a false block about a quarter of the time), and Phi((-0.02 + 0.05) / 0.0323) = Phi(0.93) = 0.82 when the true loss is 5 points. A 2-point non-inferiority test (95% two-sided lower bound, 80% power, true difference 0) needs n = ((1.96 + 0.84) x 0.25 / 0.02)^2 = 35.0^2, about 1,227 tasks (966 at one-sided 5%). The 180-session set gives SE = 0.25 / sqrt(180) = 0.0186, half-width 0.037, still wider than 2 points. No frozen set of that size exists this quarter, so the spec keeps exploratory status and the positive outcome is shadow only.
