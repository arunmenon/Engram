claim: On the P0 corpus, as later real ledger events are appended after a snapshot position S (+25%, +50%, +100% items), BM25 over the S-time document versions but with live corpus statistics fails to reproduce the S-time top-10 on at least one eligible query at one or more growth steps (the first drifting step is reported, not required to be +25%), while BM25 with statistics recomputed as of S reproduces it exactly at every step. For the vector channel, two properties are measured separately: repeatability (an arm returns the same top-10 at each growth step as that same arm returned at S) and exactness (an arm's top-10 equals brute-force exact kNN over S-valid versions). Post-filtering after ANN search is expected to lose exactness; a pinned approximate index can be repeatable without being exact, so only an exact read can satisfy an exactness requirement.

arms (same corpus, same 200 queries, same tokeniser and embedder unless the axis says otherwise; the document set in every arm is the set of item versions valid at S, including items later edited or deleted, which are read as their S-time version):
- Arm A: BM25 with live corpus statistics (df, N, avgdl from the grown corpus at each step), scoring the S-valid versions only.
- Arm B: BM25 with df, N and avgdl recomputed as of S (per-document tf and length rows with validity intervals, as in Staudinger et al.).
- Arm C: as-of vector search, HNSW over all versions at each step, over-fetch 10x k, then filter to S-valid versions.
- Arm D1: as-of vector search with the time filter applied inside the ANN search (filtered HNSW on the grown index at each step).
- Arm D2: per-snapshot HNSW index built once at S with pinned build parameters, seed, single-threaded insertion order and serialized byte hash, never mutated.
- Arm E (exact fallback read path): brute-force exact cosine kNN over S-valid versions with the pinned embedder, run at each growth step against the same stored S-time vectors. Arm E is also the exactness reference; its own repeatability is an implementation check (it must be 1.0 by construction).
- Embedding axis (applied to D2 and Arm E): pinned embedder version vs a second declared embedder version standing in for an unpinned upgrade; the second version is named in pins before any result is computed.

metric:
- primary, BM25: repro(arm, step) = count of eligible queries whose top-10 (item id, version id) list at the step equals the arm's own list at S, under the tie rule below; reported as exact count out of n and per cluster.
- primary, vector repeatability: repeat(arm, step) = count of queries whose top-10 at the step equals the same arm's top-10 at S (C, D1, D2, E).
- primary, vector exactness: exact(arm, step) = count of queries whose top-10 equals Arm E's top-10 at S; recall@10 vs Arm E at S as a secondary continuous measure.
- eligibility subsets, both reported: U = items valid at S and unchanged through +100%; H = all S-valid versions including those later edited or deleted (historical versions). The verdict uses H; U is reported to separate statistic drift from version handling.
- tie rule: scores compared as float64; ranking is score descending, then item id ascending, then version id ascending; a difference that disappears when equal-score groups are treated as unordered is reported as tie_only and still counts as a non-reproduction for the strict count.
- secondary: set equality at 10; Kendall tau over the union of the two lists; latency p50 and p95 per query per arm; storage overhead relative to the live index; for the embedding axis, repeat and exact counts across the two embedder versions.

predeclared margin: this is a contract fixture under P0's zero-violation rule, not a statistical claim; decisions use exact counts. freeze_scoring_inputs if min over steps of repro_A(H) < n and repro_B(H) == n at every step. Vector: post_filter_dilutes if at any step exact_C < max(exact_D1, exact_D2). exact_as_of_vector for an approximate arm requires both repeat == n and exact == n at every step; if no approximate arm meets both, the read path for as-of audit is Arm E (exact), and a pinned approximate index is recorded as repeatable-only, never as exact. Embedder pinning is required if the embedding-axis repeat count is below n. A null result on Arm A does not remove any pin (see negative outcome).

sample size and power note: 200 queries (120 drawn from P0 Spec retrieval logs, 80 written against the corpus at S before any growth step is computed), 3 growth steps. Drift detection needs a single failure, so the question is how small a drift rate the fixture can see. If queries were independent and a per-query failure probability p held, P(at least one failure in 200) = 1 - (1 - p)^200: for p = 1%, (0.99)^200 = exp(200 x ln 0.99) = exp(-2.010) = 0.134, so detection probability is 0.866; for p = 0.5%, exp(200 x ln 0.995) = exp(-1.003) = 0.367, detection 0.633. On a null result, the one-sided 95% upper bound on p with 0/200 failures is 1 - 0.05^(1/200) = 1 - exp(-2.996/200) = 1 - 0.98513 = 1.49% (rule of three: 3/200 = 1.5%). Queries are not independent: queries from the same Spec (or the same author, for written queries) share vocabulary and documents. So no query-level Clopper-Pearson interval is reported as inference. The only inferential bound reported treats clusters as the unit: a cluster fails if any of its queries fails, and with 0 failing clusters out of k the one-sided 95% upper bound on the cluster failure rate is 1 - 0.05^(1/k). k is not known until queries.jsonl is frozen; for illustration only (not source numbers), k = 10 gives 25.9%, k = 20 gives 13.9%, k = 40 gives 7.2%. The three growth steps are nested on one ledger and are not independent replicates; no bound is multiplied across steps. Everything else (counts, per-cluster counts, latency, storage) is descriptive. N-SURVEY-20260927-15 does not report drift magnitude on memory-sized corpora; this run measures it on this fixture only.

kill criterion: the BM25 claim is killed for this fixture (no_drift_observed) if Arm A reproduces all eligible queries in H exactly at all three growth steps; this records an observed no-drift range and does not remove the statistics pin. The post-filter dilution part is killed if exact_C == n at every step. Stop before running (not a result) if policy.md status is unset or no approved caps exist, the appended events are synthetic rather than real later ledger events, fewer than 200 queries are frozen, any query was written after a growth step was computed, the as-of tf and length rows cannot be rebuilt from the ledger prefix at S, historical versions of edited or deleted items cannot be recovered as of S, or any pin (including D2's serialized index hash) is missing.
