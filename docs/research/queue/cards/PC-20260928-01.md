claim: On long-horizon engineering tasks at a fixed context threshold, deterministic verbatim truncation (CliffCompaction rules) resolves at least as many tasks as LLM summarisation compaction at no more than its cost, and a sliding window is not worse than either.
proposed experiment: Arms, all with one frozen model and one frozen harness at a 16K compaction threshold: A = harness-native LLM summarisation compaction; B = CliffCompaction proxy at commit b48d660 with default rules; C = sliding window (system and task prefix plus most recent turns). Dataset: our P0 long-horizon engineering task set (or, if not ready, a fixed 60-task subset of Terminal-Bench 2.0 with sessions that cross the threshold), 3 attempts per task. Metrics: task resolve rate (primary) and dollar cost per attempt at a fixed price list (secondary); paired per-task bootstrap. Predeclared margin: B is adopted as default if its resolve rate is no more than 2 points below A with cost no higher than A. Kill: if B is more than 2 points below A on resolve rate, or C beats B by more than 3 points, drop truncation-only compaction and keep summarisation off only where a retrieval path back to the log exists.
why it matters for us: This tests R3 context assembly under a bounded budget with an R1 twist: a truncation is a deterministic projection of the ledger that a reviewer can replay, while a summary is a new unreproducible artifact. It also gives our first in-house on/off number bearing on B5 (summarising compaction has no published positive result).
