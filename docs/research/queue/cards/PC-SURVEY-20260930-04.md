claim: On H10's seeded history, invalidating memories at the exact changed unit (file plus changed span, or the specific ticket field) flags stale items with precision at least 0.9, while invalidating everything derived from the changed file or source has precision below 0.5 at the same recall, and leaves fewer valid memories served. Source result (N-SURVEY-20260930-07): row-level invalidation precision 1.00 on seven models; table-level 0.25 on five of seven, and first-try success on still-valid entries fell to 0 % on five of seven; stamp checks with dependency vectors cost about 0.2 % tokens, stamp-only checks cost 14 % more.

proposed experiment: Use H10's about 50 Decisions whose underlying file or dependency later changes and about 50 that stay valid. Record for each Decision a dependency at three granularities: source id only; file path plus blob hash; file path plus line range or symbol. Arms: (1) no invalidation; (2) source-level; (3) file-level; (4) span-level; (5) the decision-model staleness audit from H10a alone; (6) span-level followed by the audit on the remainder. Metric: stale-flag precision and recall, count of valid memories wrongly withheld, added tokens and latency at serve time. Kill: span-level precision not at least 0.2 above file-level, in which case file-level provenance is enough for P5.

why it matters for us: H10 already says to test plain source-change invalidation before a model-based audit, and does not say at what granularity. The published ablation shows the coarse unit throws away three valid items for each stale one and erases the benefit of memory for unaffected work. The answer fixes what P5 must store per item and what a store adapter must be able to report (versions and diffs), which is a clause of the scoped-interface contract.
