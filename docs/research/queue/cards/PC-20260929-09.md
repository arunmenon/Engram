claim: On build-time tasks whose MCP results exceed 100 KB, a Jev relevance hook that keeps only relevant segments (pass-through when the best score is below 0.5, 6,000-byte packet, verbatim recovery by id) cuts agent wall time by at least 20% and total cost including Jev tokens by at least 10% with no drop in task correctness.
proposed experiment: Arm A = Claude Code with its normal handling of oversized MCP results (no hook). Arm B = the same agent with the JevScout hook at commit a42e81b, default thresholds. Same model, same prompts, same tools. Dataset: 12 build-time tasks from our PDLC work that return large results (multi-hundred-comment tickets, long Confluence design pages, big search responses), 5 runs per task per arm. Metric: task correctness graded blind against a per-task rubric by two reviewers, wall time, total cost including TypeSafe charges, count of recovery calls. Predeclared margin: time down at least 20% and cost down at least 10% with correctness not lower by more than 1 run in 60. Kill: if correctness drops by 2 or more runs in 60 or total cost including Jev tokens does not fall, drop the hook.
why it matters for us: R3 asks for sufficient evidence within a bounded budget; this is a cheap, reversible assembly-stage test of a System One filter on exactly our build-time read pattern (priority 1). The author's report omits Jev token cost and half its tasks, so our own run is the only way to know whether the saving is real.
