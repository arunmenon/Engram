# CTO critique of the Engram decision desk

## 1. Verdict

**Partly:** I can usually understand the question and spot why a test should wait, but I cannot consistently tell what approval authorizes or why an experiment deserves scarce staff time. All nine reviews are blocking, yet four cards recommend approval, and the explanation that approval only queues work is outside the five visible fields. Nine advertised two-minute briefs would take 18 minutes before deliberation, so the cards must carry the decision conditions, product consequence and relative priority for a ten-minute desk to work.

## 2. Per brief

These decisions use exactly the fields specified in `DESK-RENDERING.md`, including only the first reviewer sentence and first two approval sentences. “Approve for the queue” below is a conditional allocation decision: I require the stated review fixes before execution; the briefs do not establish an automatic check that enforces that condition. Brief names describe the work; links identify the source without requiring knowledge of internal IDs.

### 1. Filter instructions hidden in our own summaries

Source: [Summary filtering brief](../briefs/BRIEF-PC-20260926-01-E-20260926-01-r2-v2.md).

- **Card alone: cannot decide.** The one missing thing is whether “approve” starts a blocked experiment or merely reserves a place in the queue. Catching at least 45 of 50 planted instructions, and ten more than the existing filter, is unusually concrete, but “remaining fixes are small” does not explain why approval is compatible with a blocking review.
- **After the full brief: approve for the queue, with the reviewer fixes required before execution.** The experiment is a prerequisite for enabling summaries, and doing nothing keeps those summaries away from agents. Two people-days is a plausible investment to unblock that decision, although “almost no” false blocks still needs a numerical limit before a run.
- **Hardest phrase:** “It extends the planned injection-gate test (H10b) to summaries our own model writes, and it is a precondition for the consolidation test (H9).”
  **Say instead:** “We already plan to test the filter on outside memories; this adds summaries written by our own model, which must be checked before we test combining memories into summaries.”

### 2. Check whether the handoff model memorizes repositories

Source: [Repository recognition brief](../briefs/BRIEF-PC-20260926-02-E-20260926-02-r2-v2.md).

- **Card alone: defer.** The reviewer says the main score cannot detect the very failure being tested. I do not need to understand the paper to reject that measurement plan for now.
- **After the full brief: unchanged.** Fix the scoring and session handling before bringing it back; labelled examples from at least six repositories and the test software also do not exist. The risk is clear: a model may look good on familiar repositories and make poor handoff choices on new ones.
- **Hardest phrase:** “It needs a separate repository-recognition check, a session-aware shuffle, and size limits on every outcome.”
  **Say instead:** “Check separately whether the model recognizes repositories, keep sessions intact when shuffling labels, and state how much data is required before reporting each possible conclusion.” The original should also specify what “size limits” means if that is not a minimum amount of evidence.

### 3. Make memory filters' confidence scores trustworthy

Source: [Confidence score brief](../briefs/BRIEF-PC-20260926-04-E-20260926-03-r2-v2.md).

- **Card alone: cannot decide.** The one missing thing is what operational decision changes when the scores become more accurate. The question says it “does not change which items a gate lets through,” while the recommendation says every later threshold depends on it; seven people-days needs a clearer payoff than “honest” numbers.
- **After the full brief: defer.** I now see the connection to saving memories, filtering memories and handing work to a larger model, but I still cannot tell how the fixed 50% cut-offs, the 30% to 70% handoff range and unchanged gate decisions fit together. Clarify the intended behavior and complete the measurement revision before allocating seven people-days and 900 labels.
- **Hardest phrase:** “nothing guarantees enough separate sessions in each half”.
  **Say instead:** “Set a minimum number of separate sessions in each half of the data.” Name what each half is used for; the brief does not tell me, and I should not have to infer it from a paper.

### 4. Compare model-selected evidence with strong search

Source: [Evidence selection brief](../briefs/BRIEF-PC-20260926-05-E-20260926-04-r2-v2.md).

- **Card alone: defer.** It targets a three-point improvement but can only detect gaps around eight points, and it could reach a verdict from two repositories. Even without knowing the score's unit, those are sufficient reasons to revise the test.
- **After the full brief: unchanged.** A fair comparison must include the strongest alternative, including the reranker, and enough repositories. The useful product question is whether model selection adds value beyond good search when both supply the same amount of text.
- **Hardest phrase:** “With the few hundred tasks we have it can only see gaps near 8 points, not the 3 it targets”.
  **Say instead:** “Our few hundred tasks can reliably distinguish only a difference of about eight points on the chosen score; this test is meant to detect a three-point improvement.” Then name the score and its unit. Neither is supplied here, so I cannot safely rewrite “points” as a percentage of successful tasks.

### 5. Decide when to return no memory

Source: [Empty memory result brief](../briefs/BRIEF-PC-20260926-C03-E-20260926-05-v2.md).

- **Card alone: defer.** One comparison changes two things at once, so it could attribute a bad outcome to the wrong design. The proposed decision, a separate “no memory needed” check versus allowing the ranking model to return nothing, is understandable.
- **After the full brief: unchanged.** Separate the score cut-off from the “none” option, evaluate explicit requests not to use memory separately, and use an independent judge. I also learn the current default is always to supply at least one memory; the card should expose that consequence of waiting.
- **Hardest phrase:** “the pre-check can pass just by obeying ‘don't use memory’ prompts”.
  **Say instead:** “The separate check could earn a passing score by following explicit requests not to use memory, without showing that it can recognize when no stored memory is relevant.”

### 6. Compare hosted and local memory ranking

Source: [Hosted reranking brief](../briefs/BRIEF-PC-20260926-C04-E-20260926-06-v2.md).

- **Card alone: cannot decide.** The one missing thing is how much better answers must become to justify using the hosted service. “Better answers” gives no minimum worthwhile improvement, and the only answer test cited is a tie.
- **After the full brief: defer.** The missing value threshold becomes more important once I learn that hosting sends memory text outside our infrastructure. Keep the stated local default while the comparison is made fair and the proposal states what answer improvement would justify the ongoing cost and data transfer.
- **Hardest phrase:** “keep a loss from rewriting the search belief”.
  **Say instead:** “If hosted ranking fails to improve answers, do not treat that result as proof that it cannot improve search scores.” This distinction is useful, but “the search belief” makes me decode an internal research framework.

### 7. Test links between new facts and the memories they replace

Source: [Replacement links brief](../briefs/BRIEF-PC-20260926-C05-E-20260926-07-v2.md).

- **Card alone: defer.** The spending estimate exceeds its limit, the comparison bundles changes, and prerequisites are missing. The question itself, whether replacement links help agents use current facts, is clear.
- **After the full brief: unchanged.** The record format and retrieval test setup are not built, and even a real five-point gain could remain inconclusive. Deferral does not stop the existing design from proceeding on its assumption that the links help, which is a consequential detail hidden from the card.
- **Hardest phrase:** “Fix an affordable sample plan, name or split the bundle, seal the error check, and drop claims about the other system.”
  **Say instead:** “Choose a sample that fits the spending limit, either test the two changes separately or describe them as a combined change, check errors on examples not used for practice, and stop attributing the other system's results to these links.” The brief should name the two bundled changes.

### 8. Test whether filtering changes what the agent actually does

Source: [Agent behavior safety brief](../briefs/BRIEF-PC-20260926-C06-E-20260926-08-v2.md).

- **Card alone: defer.** Passing would authorize blocking on the strength of a safety claim the test cannot support. That is enough to wait, even though “the headline safety number” is not visible on the card.
- **After the full brief: unchanged.** Related instruction variants are counted as if they supply more independent evidence than they do, only one group removes hidden characters, and ordinary task performance has no required minimum. Those are material conditions for enabling blocking, not just wording fixes.
- **Hardest phrase:** “the real guarantee is near 10%, not under 2%”.
  **Say instead:** “The 150 planted instructions represent only about 30 distinct wording families, so the claimed safety bound is about 10%, not below 2%.” The writer must also name what event the percentage bounds and the confidence level; neither is stated, so “guarantee” is not a useful substitute.

### 9. Test whether storing reasons helps find outdated decisions

Source: [Decision reasons brief](../briefs/BRIEF-PC-20260926-C07-E-20260926-09-v2.md).

- **Card alone: cannot decide.** The one missing thing is whether “approve” only queues work or allows the test to run with its blocking scoring flaw. Comparing reasons, bare facts and a two-week age flag is clear, and the small budget makes this worth considering once that distinction is explicit.
- **After the full brief: approve for the queue, with the reviewer fixes required before execution.** The result informs an imminent choice about whether every writer must supply a reason, and the recommendation explicitly limits the result to an initial indication. Reasons must have been written before the items became stale, which is a useful protection against manufacturing an easy test after the fact.
- **Hardest phrase:** “Apply the recall floor to every rule, change only the reason between forms, and treat negatives as defaults.”
  **Say instead:** “Every rule for declaring a winner must require finding a minimum share of stale items; compare records that differ only in whether they include a reason; if the test finds no benefit, keep the current default without claiming that reasons never help.” State the minimum share as well.

## 3. Patterns

### 1. The card hides the meaning of the decision

All nine full briefs say, “Approval only queues it; nothing runs until you set the standing policy.” It is the third sentence under approval, so the rendering rule drops it. Meanwhile all nine cards say “blocking,” and four say “Approve.” “Blocking, but the remaining fixes are small” and “Blocking, fixable: measurement details, not the idea” do not establish who must fix what before work can start. Put the scope of approval and its conditions in the visible fields; define the policy elsewhere on the desk in words the CTO can act on.

### 2. Internal vocabulary survives the plain-English questions

The questions often work well: “Do ‘this replaces that’ links make agents answer with current facts?” needs no paper or internal ID. The explanations revert to “the planned typed-graph test (H7),” “Spec-time curator,” “the escalation band,” “seal the error check” and “treat negatives as defaults.” These mix product components, statistical methods and internal bookkeeping without explaining their roles. Even the reference labels are unhelpful: one brief describes H5 as the escalation test, while another cites H5 among the tests supplying logs for two memory gates. I should not have to resolve that mapping to approve research.

### 3. Numbers lack the meaning needed to choose

“8 points, not the 3 it targets” does not name the score. “Near 10%, not under 2%” does not name the bounded event or confidence level. “Calibration error about threefold” does not say what improvement in agent behavior would matter, and the reviewer explicitly says the proposed measure differs from the paper's. The 94% versus 87% search result is quantified precisely but cannot establish the answer improvement the hosted-ranking proposal needs. Give each decision-critical number a unit, comparison and consequence; keep paper results distinct from local success criteria.

### 4. Reviewer summaries ask the CTO to finish the research design

The first reviewer sentence is often a useful alarm, but it rarely provides a condition for release: “the comparison is not yet fair,” “the budget does not close, and changes are bundled,” and “the main score cannot see the failure it hunts.” The full text then gives compressed instructions such as “size limits on every outcome” or “name or split the bundle,” without naming the required amount of data or bundled changes. A CTO can decide to wait from these warnings, but cannot tell whether the next revision has done enough. State the consequence of the flaw and the check that will clear it.

### 5. Repetition consumes space that should distinguish priorities

The evidence grade repeats between the card's grade word and several full-section openings, while the underlying paper often appears in both “Why now” and “Evidence.” For example, the hosted-ranking brief repeats the tied answer test, and the replacement-links brief repeats that a whole-system comparison did not isolate the links. “Approval only queues it” is repeated nine times but still absent from the cards. Meanwhile “It is the cheapest here” and “It is the costliest of these” lack a common cost basis: the reason-storage test uses two people-days versus 1.5 for the repository test, and replacement links use four versus seven for confidence calibration. Machine use could explain those claims, but no common money estimate is supplied; even “Small” three-day work and “Medium” two-day work are not explained.

## 4. What is missing that a CTO needs

- **The exact action being authorized.** Is this a queue position, staff allocation, permission to collect data, permission to execute, or permission to change production behavior after a pass? The full briefs explain queueing but not what setting the “standing policy” entails or how blocking reviews are cleared.
- **A defined defer action.** Name who revises the proposal, the specific conditions for returning it, the date or event that triggers reconsideration, and whether revision work consumes an approved budget. “One quick revision away” is not a commitment. Distinguish waiting for resources from refusing the present design.
- **The consequence of doing nothing on the card.** Most full briefs already provide one: summaries stay off, local ranking remains the default, reasons remain optional, or replacement links proceed on an untested assumption. Surface those existing facts. State any unresolved consequence instead of implying every delay is equally costly.
- **A desk-wide order of work.** Summary filtering depends on the broader filter work, confidence calibration needs gate trial logs, and both ranking proposals touch the same planned test. Show which experiment unlocks another, which can share data or test software, and which product decision has a real deadline. Proposed verdict dates alone do not establish priority.
- **An accountable owner and credible capacity estimate.** No brief names who runs it or who clears the review. Say whether the quoted days include building missing test software, assembling data, labelling, review fixes and analysis. Explain what makes a result due on 6 November achievable when its prerequisites do not exist.
- **A minimum worthwhile result and its consequence.** For each possible result, say what Engram would do next and what would remain uncertain. Hosted ranking needs an answer-quality threshold worth its cost and data transfer; summary filtering needs a numerical false-block limit; reason storage needs the minimum share of stale items it must find. Weak prior evidence can justify an experiment, but does not define a passing result.
- **Comparable total cost and limits.** Give staff time, estimated money, ongoing product cost where relevant and a spending ceiling on the same basis. Identify any budget that is knowingly exceeded. “No model spend” still leaves seven people-days competing with other work.
- **The evidence's scope, without requiring another click.** The briefs deserve credit for saying “originals unchecked,” distinguishing opinions from measurements and admitting domain differences. The CTO still needs one sentence connecting that limited evidence to this experiment's value, rather than to an unnamed “current belief.”

## 5. Rewrite one

I chose the confidence-score brief because its readable 70% example conceals three different operational decisions and an unresolved statement about whether behavior changes. The rewrite preserves the author's recommendation, all substantive facts, numerical values, qualifications and internal cross-references; my own decision remains defer for the reasons above. It does not invent a benefit threshold, a session minimum or a resolution of the behavioral ambiguity.

### Five-line card

Each numbered line below is one renderer field, even if it wraps on screen. The wording follows the rewritten sections below; the queue restriction is now within the first two approval sentences.

1. **Question:** Can the confidence scores used to decide which memories to save and which to pass to agents reliably describe how often those decisions are correct? A score of 70% should mean about 70% correct for chat, documents and tool output alike. The proposal changes the confidence numbers, not which items the filters let through.

4. **Reviewer:** Blocking: fix how error is measured, require enough separate sessions in each half of the data, and report worsening results separately from no improvement.

### Seven sections

#### Where this fits in Engram

This work checks the confidence scores of two filters: one decides what memory to save, and the other checks memory before agents receive it. It uses logs from their planned tests, referenced internally as H5 and H10b. It sets how their decision thresholds are chosen, rather than opening a new research question.

#### The question

Can the confidence scores used to decide which memories to save and which to pass to agents reliably describe how often those decisions are correct? A score of 70% should mean about 70% correct for chat, documents and tool output alike. The proposal changes the confidence numbers, not which items the filters let through.

#### Why now

Both filters' thresholds depend on these scores, as does the range in which the cheap model hands work to a larger one. That handoff happens when the cheap model is 30% to 70% sure, so those percentages must be trustworthy. If we skip this work, both filters keep a fixed cut-off of 50%.

#### Evidence

Moderate: one controlled paper in an unrelated domain. Adjusting confidence scores to the local data reduced calibration error by about a factor of three on police crash reports, using the same small decision model we use. Calibration error measures the mismatch between confidence scores and observed correctness. The result supports our view that vendor confidence scores are claims whose accuracy still needs to be demonstrated.

#### Reviewer

Blocking: fix how error is measured, require enough separate sessions in each half of the data, and report worsening results separately from no improvement. These are fixable measurement problems, not an objection to the idea.

The proposed error measure differs from the paper's, so the paper's estimated improvement cannot be carried over. Use the same measure or justify the difference. Neither half of the data is guaranteed to contain enough separate sessions; set a minimum for each half. The current rules classify a worse result as “no gain”; report harm separately.

#### If you approve

Medium: about seven people-days, mostly for labelling, with no model spend; approval only queues the work, and nothing runs until you set the standing policy. A verdict could arrive by 13 November, once logs from both filters' trials exist and 900 items have been labelled by source.

#### Suggested action

Approve. There is no model spend, the review fixes concern measurement, and every later decision threshold for these two filters depends on trustworthy confidence scores.

## 6. Concrete rules for the writer

1. Make the five visible fields sufficient to identify the product choice, recommendation, cost, consequence of waiting and exact scope of approval.
2. For a blocking review, state what must change before execution and why the recommendation is approve or defer despite that block.
3. Name components by their job in Engram; keep internal experiment IDs in optional references and explain necessary technical terms on first use.
4. Give every decision-critical number its metric, unit, comparison and practical meaning; distinguish published results from proposed pass criteria.
5. State what a win, loss or inconclusive result changes, including the default that remains if no useful evidence arrives.
6. Name an owner, prerequisites, budget coverage and a return date or trigger; define the work that defer authorizes.
7. Compare desk items on a common cost basis and expose dependencies; never claim cheapest, costliest or urgent without that basis.
8. Give each section one job, remove repeated evidence, use plain English and avoid em dashes.
