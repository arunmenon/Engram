# ToolFence: Fine-Grained Authorization for Secure Tool-Using LLM Agents (arXiv 2609.37196)

- **URL:** https://arxiv.org/abs/2609.37196 (full text read at https://arxiv.org/html/2609.37196)
- **Type:** paper (cs.CR)
- **Author / org:** Yanjie Li, Xiangyu He, Xuelong Dai, Bin Xiao. Hong Kong Polytechnic University; Shandong University.
- **Date:** 2026-09-29 (v1)
- **Retrieved:** 2026-09-30, arXiv HTML v1. No code repository listed; the paper says evaluation artifacts will be released with safeguards.
- **Cited by evidence:** https://x.com/gastronomy/status/2105126595128135828 (@gastronomy, abstract repost; link https://ift.tt/kXZ3YHB resolves to the arXiv abstract). Memory digest of 2026-09-30.
- **Relevance to a memory stack:** medium. It is about tool calls, but the mechanism (a value may fill an authority-sensitive slot only if its provenance is the user or a named source) is the same rule we need when recalled memory supplies arguments to an action.

## TL;DR
- Before the agent reads any external content, an LLM "policy architect" compiles the authenticated user query into a typed blueprint of capabilities: which tool, which effect class, and for each parameter which provenance is allowed.
- A deterministic monitor then checks every proposed call in code: capability match, provenance of each argument, call budget. No model is called on this path.
- When the blueprint is incomplete, a judge is asked to grant a new capability shape. The judge sees the shape, "NOT concrete argument values" (as summarised from the paper), so injected text in arguments cannot argue with it.
- AgentDojo, Qwen3-max: overall attack success 0.20% (CaMeL 0.42%, no defence 21.20%), clean utility 38.90 against 42.70 undefended (a 3.80 point drop) and 32.67 for CaMeL. Runtime 1.90x against CaMeL's 12.95x.
- The post is the abstract; its numbers match. No claim correction.

## What it claims / describes

**Blueprint.** P = (M, C). Tool manifest M labels each tool's effect: `read`, `local_compute`, `communication`, `financial`, `external_write`, `delete`. Each capability in C is a tuple (tool, effect, parameter bindings, call budget, reusable flag). A parameter binding states the allowed provenance: `literal` (from the user query), `derived` (from a named source tool's output), `template` (an authenticated pattern), `free` (non-sensitive). Compilation uses "only the authenticated query and controller-owned tool schemas", never untrusted observations. The compiling model is the same backbone as the agent.

**Provenance labels on values at run time.** `user` (the value occurs verbatim in the authenticated request), `tool:<name>` (copied from that tool's earlier output), `model` (generated by the agent with no prior source).

**Deterministic monitor.** Three checks: the call is covered by a capability; each argument's provenance satisfies its binding; the budget is not exceeded. User-grounded read operations are auto-allowed.

**Runtime grants.** A judge (same LLM as the agent) approves a new capability only if it serves the authenticated request and every authority-sensitive parameter is bound to `user` or a named `tool:` source. It refuses when an authority-sensitive parameter would have `model` provenance.

**Cross-session cache.** Stores value-free signatures (tool, effect, parameter to binding and source tools). Per-call binding checks still run; cached shapes carry no concrete values across sessions.

**Threat split.** Cross-tool attacks (make the agent call a tool the user did not want) versus within-tool attacks (keep the intended tool, change its arguments). 609 user-attack pairs: 524 cross-tool, 85 within-tool, six injection strategies (Direct, Ignore Previous, Important Instructions, InjecAgent, System Message, Tool Knowledge).

## Mechanism details you could implement
- Classify every tool by effect class and mark which parameters are authority-sensitive (recipient, amount, URL, path, id).
- Tag every value flowing through the agent with one of `user`, `tool:<name>`, `model`. A value is `user` only if it appears verbatim in the authenticated request.
- Deny in code any call whose authority-sensitive argument is `model`, or `tool:<name>` from a source the request did not name.
- Ask a model only for capability shapes, never for a verdict on concrete values; cache approved shapes without values.
- Count calls per capability and stop at the budget.

## Limitations, caveats, counter-evidence
- Stated by the paper: "Utility loss can arise when a legitimate authority-sensitive value is available only through untrusted content", for example a URL found in a web page is not auto-allowed for a following fetch. And: "ToolFence verifies where a value comes from, but not whether the model's choice among multiple authorized values faithfully reflects user intent."
- The policy architect and the judge are the same model as the agent; a compromised or weak model compiles a weak blueprint (inference).
- One benchmark (AgentDojo); no adaptive attacker that targets the blueprint compilation step.
- Verbatim-match provenance for `user` values will miss paraphrased or normalised values (inference).
- No code; no variance.
- Related evidence already on the bus: PACT (note paper-pact-argument-level-provenance-2605-11039.md) makes the same argument-level provenance point. ToolFence is a second, separate group reaching it, with a runtime comparison against CaMeL.

## Takeaways for tuning a memory stack
- A recalled memory is an untrusted observation. If it supplies an argument to an action, that argument's provenance is `tool:memory`, and an authority-sensitive slot should accept it only when the user's request named memory as the source.
- A content gate on served memory (B24) and an argument-provenance check are different controls; the second catches the case where the memory text looks like a harmless fact but carries the attacker's recipient or path.
- Keep the fast path deterministic; spend model calls on shapes, and cache them.

## Open questions
- How does verbatim user provenance behave with long structured requests where values are derived (dates, ids looked up)? Not reported beyond the stated limitation.
- What is the utility cost on coding-agent tasks, where most arguments are model-generated? Not tested.
