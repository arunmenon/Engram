# Independent review request: a federated memory stack for an enterprise AI-engineering programme

You are reviewing an architecture position before it is taken to the programme that would adopt it. Be adversarial. Your job is to find where the position is wrong, over-claimed, under-evidenced, or strategically naive, and to say what you would do instead. Do not summarise the material back. Do not soften findings. Where you agree, say so in one line and move on.

This prompt is self-contained. You do not have access to the internal documents; everything you need from them is quoted or paraphrased below. Treat quoted programme text as ground truth about what the programme wrote, not as truth about the world.

---

## Part A — The situation

**The programme.** A large company's CTO-wide programme for building software with AI coding agents. It deliberately does not standardise on one agent harness; it builds a shared foundation (identity, security, enterprise integration, measurement, evaluation, governance) plus **eleven interoperability contracts (C1–C11)** that any conforming harness plugs into. Three harnesses exist today with different shapes: a scripted one-ticket-to-one-PR pipeline, an always-on autonomous agent loop, and a third. Roughly 25–30 engineers, five workstreams, a three-month commitment window, one organisation required to adopt.

**The spine** every change flows through: Request → Intake (Spec, Decompose, Sequence) → Inner Loop (Design, Implement, Self-review, Test; opaque to the outer loop) → Pull Request (adversarial review, merge) → CI/CD (fast tier, batched tier, per-environment gates) → Operating (deploy, observe, detect, diagnose, mitigate, RCA) → feedback (escapes, RCA) back to Intake.

**Company Knowledge** is a separate workstream that both loops call into from four sites: the Inner Loop's Spec step ("what domain and tribal knowledge does this run need, before Design starts"), Intake triage (ticket corpus and org structure for routing), Intake specification ("a Spec references rather than inlines knowledge; Company Knowledge resolves that reference at build time"), and PR review ("adversarial review runs with the same knowledge that crafted the spec, pinned as a snapshot"). It provides "the facts a human author would fill in silently, and an agent with no organizational context cannot."

**Contract C6, verbatim:** *"An agent reads, writes, and retrieves through one interface. The scope of each operation is declared. The store stays where it already lives. We integrate with the store. We do not absorb it. Test: a change of backend touches no harness code."* Three obligations: one interface (not one store), declared scope per call, backend independence proven by a passing swap test. **C6 has no ratified holder.** Neither does C9 (Evidence and Eval: every stage emits agreement, autonomy, quality, speed, cost signals; autonomy rises only after eval).

**The proposed C6 interface** (from the programme's own reference architecture): three verbs, `retrieve(query, scope, kind)`, `write(record, scope, kind)`, `snapshot(scope, as_of)`. `kind` closed at fact / episode / document; skills explicitly do *not* go through C6. `scope` mandatory: caller identity, space/domain, classification tier. Only certified callers write a fact; any caller writes an episode. Response normalised to content, provenance, freshness, confidence. `snapshot` is "a versioned, signed view of everything a scope could retrieve at a point in time" and "does not exist in any repo surveyed as a first-class operation today… the single largest gap." It is required by an already-decided fitness function: *"Buildability is a property of the spec and the knowledge configuration it runs in, never the spec alone"*; the adversarial reviewer runs against a pinned config (model, prompt, knowledge snapshot, thresholds) so scores stay comparable.

**The fault-adjudication rule**, the one testable failure mode the programme gives Company Knowledge: if a failure was not recoverable and the missing piece was spec-type information, the fault is the spec; if the missing piece was tribal knowledge, the fault is Company Knowledge; if it was recoverable but the agent chose wrong, the fault is the harness. Ambiguities the agent resolves by inference are recorded in an **assumptions ledger**, and "a gap only counts against Company Knowledge when the assumptions ledger shows the missing information was tribal, not structural."

**The knowledge-gap loop:** because every retrieval is scoped and snapshotted, an adjudication agent can replay what the interface returned; every confirmed gap is written back as a candidate Fact through a certification path.

**The programme's own due diligence** over eleven internal repos concluded: "No single repo is a ready-made C6 knowledge interface. [The strongest service candidate] is itself one backend, not the adapter layer the contract requires. [Another system] is the strongest contract-shape prior art but is a black box. The interface itself does not exist yet anywhere in the estate."

**What has since surfaced** (a refresh one day later): (1) a live MCP gateway from the same org as the author of this position, with `retrieve` and a work-in-progress `write`, an `evidence[]` response carrying `validity{status, last_updated, verified_by, expires_at}`, rank-fused scores, scope *optional and default-open*, `content_type` that *includes skills* (contradicting the resolved decision), no snapshot, no receipts, permissioning "under consideration"; it is cited nowhere in the programme's pages and is not in the due diligence. (2) The "black box" is a production knowledge service behind two of the three harnesses (thousands of users, thousands of repos), with strong per-call scope, mandatory repo/branch/path/line citations, absolute read/write separation, around fifty tools, and no snapshot. (3) A separate, differently named "memory service" from another org is heading to production and is what the programme's pages mean when they say a name that happens to collide with the author's system. (4) The author's system appears in none of the programme's due diligence.

**The harnesses' memory today**, source-verified by the programme: the scripted harness has no retrieval at all and its memory modules are stubs returning empty. The autonomous harness has a real embedded knowledge base with a priority-boosted similarity score, but its "memory" store has never actually run semantic search in production, and a second, unconnected store does the searchable writes.

**Ontology.** A separate page raises eleven dimensions (domain vs practice as a tag set; format plurality; granularity; retrieval-and-ranking-as-classification, with the open question of whether ranking-derived classification should be written back or stay a runtime signal; and others not yet captured), proposes no schema, and asks whether the schema should live in one backend or be a gateway-level concern all backends normalise into.

## Part B — The author's system and its research position

The author has a memory/context-graph service (call it **PCG**): an immutable, positioned event ledger (append-only stream with global positions, idempotent ingest, tenant scoping) as source of truth; a derived, rebuildable property graph (event, entity, summary, belief, goal, episode, workflow and user-model node types; temporal, causal, semantic, entity, supersession and provenance edges) as a query projection; four asynchronous consumers (structural projection, LLM extraction at session end, embedding enrichment, scheduled consolidation); intent-weighted retrieval; a four-factor time-decay score with retention tiers; and a response format in which every node carries a provenance block (source event id, stream position, session, agent, trace, time) and scores. Ports-and-adapters structure. The application layer has known scale defects and unproven retrieval claims; a code reset is assumed, so evaluate the design, not the code.

The author's research position after a two-week literature and evidence pass (about sixty papers and repos, September 2026):

1. **Ledger first.** Raw, verbatim, positioned storage is the bank; read-time, task-conditioned curation beats write-time distillation; the graph is an index for lineage, supersession and entity questions, not the default read surface. Graph-vs-vector lift is unproven at matched budget and must be measured, not assumed.
2. **Receipts.** Every retrieval and every automated decision emits a ledger event (what was asked, what was served, which backends, distributions, thresholds, model version). Almost no memory system does this; it is required by the feedback loop, by any typed-decision layer, and by the adjudication rule above.
3. **Gated, explicit updates.** Memory writes are proposals; an independent judge accepts, supersedes or rejects; supersede on two signals (contradiction ≥ threshold *and* a named target), never delete; the old version stays and is excluded from default recall.
4. **Outcome loop.** Reinforce memories that contributed to successful outcomes, not memories that were merely returned; measure the feedback-loop rate (wrong memories whose weight increased), which no published system reports.
5. **Provenance and staleness as first-class.** Per-item source class, recorded time and reason; a periodic "still true given the current snapshot?" audit that flags and never deletes; an injection gate on served memory, since extracted items came from untrusted transcripts and are re-injected into prompts.
6. **Typed decisions on closed menus.** A small "System One" decision model (yes/no, choice over ≤255 options, ordinal score; sub-second; assumed available in-house) placed at judgment points whose options are a closed, freshly rebuilt menu: route across backends, listwise rerank, sufficiency stop, per-item confidence, write admission, supersession, fault adjudication, staleness, injection. Never for generation, never for numeric or temporal reasoning, never alone in an open loop (field evidence: planner + decider won 9/10, decider alone 0/10). Thresholds fitted on own labelled data, never copied; the cheap battery first, escalation only when a held-out split shows it helps (field evidence: the larger battery scored lower). Listwise choice beats per-item yes/no (0.94 vs 0.87 recall@1, 30× fewer calls); never give a gate a "none relevant" option; pruning off by default.
7. **Consolidation and decay are unproven.** No source reports consolidation on-vs-off; the only measurement is negative. No source shows forgetting helping. Both are hypotheses to measure, not features to sell.
8. **Evaluation discipline.** Noise floor from repeated baseline runs; held-out split with knowledge-update, contradiction and abstention cases; one attributable change per round; frozen judge; experiment ledger outside memory; charge memory for its tokens.

## Part C — The position under review

**Claim 1. The target is a federated memory ecosystem, not a store.** Ten layers: systems of record (never absorbed); capture (OTel GenAI spans, assumptions-ledger writes, outer-loop outcome events); ledger; backends (a registry of heterogeneous hubs, including the production knowledge service, the other org's memory service, the author's graph, ticket corpus, signed catalogues); a federation gateway; read-time curation; write and certification; evidence and eval; governance; harness adapters. The author's assessment against C6's requirements: 3 layers "have", 14 "extend", 17 "absent", the absences being almost entirely *around* the store rather than in it.

**Claim 2. The federation gateway is the product, and it is a query planner over a registry, not a consolidation.** Components: backend registry with capability manifests (kinds served, scopes, freshness SLA, native `as_of` support, entitlement model, cost/latency); deterministic scope resolver whose output is the closed menu for everything downstream; planner (which backends, per-backend budgets, rounds; the LLM sets intent, the decider makes per-item choices); fan-out and reciprocal-rank fusion; one listwise rerank, always ≥1 item, no "none" option; normaliser (content, provenance, freshness, confidence, ontology tags); **snapshot composer**; receipt writer; served-memory guard (injection gate, tier redaction); fallback plane (every model-backed decision has a rule fallback and a latency budget, and the receipt records which ran).

**Claim 3. `snapshot` is the ledger's decisive contribution and the reason a positioned event log belongs at the centre.** For backends with positions, pin the position. For backends without (most of them, including wiki pages and the production knowledge service), *materialise* the returned items into the ledger and pin that; the snapshot manifest is the set of per-backend pins plus content hashes, signed; `as_of` resolves against manifests, never live backends. Three independent absences (the eleven-repo survey, the live MCP gateway, the production knowledge service) confirm nobody has this.

**Claim 4. Thirteen typed-decision points belong in the gateway** because every gateway choice is over a closed menu: retrieve-at-all; route across backends (one batched call over the registry after scope resolution); budget split; listwise rerank; sufficiency stop; per-item confidence (ordinal score over content, provenance, freshness, agreement); ontology tagging at serve time; injection gate; write admission (fact / episode / none, plus source class); supersession; **fault adjudication** (spec / tribal / harness over the assumptions-ledger entry and the replayed receipt: the cleanest decision in the set); staleness audit; cross-hub duplicate/conflict. Each with a rule fallback and a latency class; synchronous ones budgeted in the low hundreds of milliseconds; thresholds fitted on the programme's own labels (≥40 per battery before refitting); model version pinned and recorded in the snapshot manifest so buildability scores do not drift when the decider changes.

**Claim 5. The plan's shape does not shrink because of what surfaced.** The live MCP gateway is an early artefact (two verbs, no scope, no snapshot, no receipts, no registry) and is the *seam* where the MCP projection and response schema converge so the org ships one surface, not a reason to build less. The production knowledge service is a backend and the right second backend for the swap test. The other org's memory service is a certified-fact backend behind the gateway, which turns a name collision into a division of labour. The unowned-contract problem is now an unowned-*arbitration* problem, and the gateway-level schema plus the snapshot manifest are the neutral ground: they require nothing of the three except a manifest and pinnability.

**Claim 6. Sixteen components nobody has**, in build order: conformance kit (three verbs, scope schema, response schema aligned with the live gateway's `evidence[]`/`validity`, swap test); registry and manifests; scope resolver; snapshot service; receipt store and replay tool; assumptions ledger; outer-loop outcome ingest with a join key; certification path; fault-adjudication service; read-time curate step; staleness sweep and freshness field; systems-of-record connectors emitting positioned events (chat first, since neither harness serves it); harness adapters (capability injection, MCP-as-CLI, ticket-link resolution for the scripted harness); eval harness with pinned reviewer config; gateway-held ontology schema registry; governance console.

**Claim 7. Twelve-week sequence.** Conformance kit and a scripted-harness demo (Spec stores a snapshot id) by week 3; registry, second backend, passing swap test, fusion, receipts, converged MCP surface by week 5; materialised snapshots for position-less backends and PR-review re-resolution of the Spec's snapshot by week 7; route/rerank/confidence in shadow with receipts and fault adjudication on a labelled set by week 9; certification, supersession, gap write-back, staleness, chat connector by week 11; C9 signals joined to receipts, eval harness, noise floor, first hypothesis numbers by week 12.

**Claim 8. What the author's system stops claiming:** the graph as default read surface; decay as a differentiator; "memory system" as the category (the empty category is *federation with snapshots and receipts*); and its current name.

## Part D — What to review

Answer each numbered question directly. Where you disagree, give the strongest counter-position and what evidence would settle it.

**Architecture**
1. Is a federation gateway over heterogeneous hubs the right response to "integrate, do not absorb", or is it a consolidation wearing a registry? Where does the query planner become the new monolith?
2. Materialise-and-sign for position-less backends: is that a legitimate snapshot or a copy that violates "the store stays where it lives"? What retention, consistency and legal problems does materialising wiki and ticket content into a ledger create? Is there a design that gives point-in-time reads without copies?
3. Is the immutable positioned ledger actually necessary for `snapshot`, or would a manifest of (backend, version-or-hash) pins over the backends' own versioning suffice? If the latter, what is left of Claim 3?
4. The response schema: is adopting the live gateway's `evidence[]` + `validity{status, last_updated, verified_by, expires_at}` right, or does it bake in one backend's certification model? How should `confidence` be defined so that it is comparable across backends that compute nothing alike?
5. Scope resolution as a purely deterministic step that produces a closed menu, with least-privilege intersection across hubs: where does this break? Consider a Spec that references knowledge the reviewer is not entitled to see.
6. Read-time curation (task-conditioned briefing from raw evidence) at the Spec call site vs write-time summaries: which is right for a *build-time* dependency where the reviewer must later re-resolve the same snapshot? Does curation break reproducibility?

**Typed decisions**
7. Which of the thirteen decision points should *not* be a decision-model call, and why? Be specific about route, confidence and fault adjudication.
8. Fault adjudication as a three-way typed choice over an assumptions-ledger entry and a replayed receipt: is the label actually decidable from that state, or will "tribal vs structural" turn out to need the very knowledge that was missing?
9. The claim that a listwise choice with no "none" option and pruning off is safer than per-item gates: what is the failure mode in a *build-time* setting where returning an irrelevant fact costs a wrong implementation, not a bad chat turn?
10. Confidence from an ordinal score over (content, provenance, freshness, agreement): is this a real signal or a laundering of rank position into a number the caller will misread as a probability?

**Strategy**
11. The position says the plan does not shrink because a live two-verb gateway and a production knowledge service exist in-house. Is that right, or is it the author refusing to accept that the interface layer is already being built by someone else? What would you do in the author's place in week 1?
12. The name collision: the programme's pages use the author's system's name for a different system that is heading to production. How much does this matter, and what is the least costly fix?
13. Three months, one adopting organisation, C6 and C9 unowned. Is the twelve-week sequence credible for 4–6 engineers? What would you cut, and what would you refuse to cut?
14. Is "a running conformance kit with a passing swap test" a plausible ratification artefact for an unowned contract in a large company, or is that an engineer's fantasy about how contracts get owned?
15. The neutral-ground argument (Claim 5): does a gateway-level schema plus a snapshot manifest really require nothing of the three existing systems, or does registering with a manifest and being pinnable amount to asking each of them to subordinate?

**Evidence and risk**
16. Which claims in Part B are load-bearing for Part C and rest on the weakest evidence? Rank the top five.
17. What is the single most likely way this fails in month two?
18. What is missing entirely? Name components, risks or stakeholders the position does not mention.

## Part E — Format

- Numbered answers matching Part D. Verdict first, then reasoning. Bullets over prose.
- Close with: the three changes you would make to the position before it is presented; the one claim you would drop; and the one thing you would add.
- Under 2,500 words. No preamble.
