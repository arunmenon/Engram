Engram · context graph · engineering walkthrough

Ontology packs and the Spanner backend

This is a large refactor in two parts. First, the graph's schema is now data rather than code: a common ontology layer that every deployment shares, plus domain "packs" written in YAML. Second, every storage call now goes through five ports, and Spanner is one of the backends behind them.

ADR-0018 · ontology packs ADR-0019 · pluggable storage backends
Overview

The big picture

Schema as data

A common layer describes agent memory. Domain packs add their own types, rules and question types on top, with no engine code.

The PDLC pack

The first domain pack. It traces work from a request to code, tests, releases, deployments and incidents, and cites a source for every answer.

Storage behind ports

The ledger, the subscriptions, the graph and the search indexes sit behind five interfaces. Redis with Neo4j, an in-memory backend and Spanner all implement them.

Overview

Words used here

ledger
The append-only log of events. It is the source of truth. The graph is built from it and can be rebuilt from it.
projection
Turning events into graph nodes and edges. A worker does it asynchronously.
pack
A YAML file that declares a domain: its node and edge types, how events become graph writes, and how questions about it are answered.
port
A Python interface (typing.Protocol) that a storage backend implements. Application code only ever calls ports.
intent
The kind of question being asked, such as why or trace. It decides which edges matter.
seed
A starting node for a search, found by ID, keyword or vector similarity.
walk
Following edges out from the seeds, within depth and size limits.
admission
The final filter that decides what goes into an answer, for example dropping superseded or untrusted items.
stub
A placeholder node created when an edge points at something that hasn't arrived yet. It is filled in later.
Atlas response
Engram's standard answer shape: nodes with provenance and scores, edges, pagination and meta.
Ontology

The common layer and domain packs

The ontology has two layers. The common layer is always loaded and is the same in every deployment. Domain packs sit on top and are chosen by configuration.

The common layer: core, memory and user

These three packs together are Engram's existing agent-memory schema: 11 node types and 20 edge types. They always load first, and a deployment can't replace them.

  • core holds the event model: Event, Entity, Summary, the edges between them, the event types, and the seven core intents (why, when, what, related, general, who_is, how_does).
  • memory adds beliefs, goals and episodes.
  • user adds profiles, preferences, skills, workflows and behavioural patterns, plus the personalize intent.

The common layer describes agent memory, but it doesn't drive it yet. Event nodes and the FOLLOWS and CAUSED_BY edges are still written by the original projection code, and a test keeps the packs and the code identical. Only domain packs are written by pack rules.

What every domain pack gets from the common layer

Shared piece What it means for a domain pack
Lifecycled A type with states (open, merged, done...) gets status and status_changed_at. The pack lists which states mean "no longer current" (superseded_states), and retrieval leaves those out.
Sourced Every node and edge records source_trust: trusted or untrusted, taken from an allowlist of sources and never from the content.
DERIVED_FROM Added automatically. Every node a pack writes gets an edge back to the event that caused it. That is how answers cite their sources.
SUPERSEDES, CONTRADICTS Core edges that a pack can extend to its own types, for example "this decision replaces that one".
Claim, Anchored, Versioned Shared property bundles: confidence and method, source location and content hash, version number.
Admission rules Shared filters such as "drop superseded" and "drop untrusted unless backed up". If several packs set the same rule, their settings are merged.

Rules for domain packs

  • A pack declares what it needs, for example requires: core>=1.1. The registry loads the common layer first, then domain packs in dependency order.
  • A pack can add types, edges, event types and intents. It can extend core edges to its own types, and add weights to a core intent (PDLC adds its edges to why and who_is).
  • A pack can't override a common-layer pack, reuse another pack's names, or set the same weight twice.
  • The registry computes one version hash for the whole set of loaded packs. The graph records that hash. This is what "the graph depends on the ontology version" means in practice.

Choose domain packs with CG_ONTOLOGY_PACKS (default pdlc), and add folders of your own packs with CG_ONTOLOGY_PACK_DIRS. An invalid pack stops the API and the worker from starting, and every problem is reported at once. GET /v1/ontology shows what's loaded and whether the graph has been built and evaluated for it.

Ontology

What a pack declares

Section What it says
types Node types (key fields, properties, lifecycle states) and edge types (allowed endpoints, properties)
events The event types this pack owns
projection Rules: when event X arrives, upsert these nodes, move this state, draw these edges
extraction What an LLM may propose from free text, with a confidence ceiling, and what it must never propose
retrieval Intents with keywords and edge weights, seed types, ID patterns, and admission rules

A projection rule reads like this. When a change is merged, upsert the Change, mark it merged, and link it to any ticket key found in its description: 

- event: pdlc.change.merged
  upsert:
    - {type: Change, key: {repo: $.repo, number: $.number}, set: {merge_sha: $.merge_sha, title: $.title}}
  transition: {type: Change, to: merged}
  edges:
    - type: IMPLEMENTS
      from: {type: Change, key: {repo: $.repo, number: $.number}}
      to_each: {type: WorkItem, key: {tracker: jira, external_key: "regex($.body, 'fixes\s+([A-Z]+-\d+)')"}}
      set: {confidence: 1.0, method: declared, link_status: confirmed}

Values like $.repo come from the event. A small expression language covers paths, regex, sha256 and lists. Regexes have a time limit per match.

Ontology

Changing a pack safely

Because the graph depends on the pack version, changing a pack is treated like a schema migration. When the worker starts, it compares the loaded packs with the version the graph recorded and classifies the difference. The pack's version bump has to match.

Kind Example What happens
additive New type, property or intent Applied live
mapping A projection rule gains or changes a part Affected events are replayed from the ledger (run one projection replica while it does)
breaking Removing a type, edge, key or state; changing an identity Start-up is refused unless CG_ONTOLOGY_ALLOW_BREAKING is set; do a blue/green rebuild

Blue/green rebuild

  1. Run python -m context_graph.ontology rebuild --target CG_KEY=VALUE against a new, empty graph. It replays the whole ledger with the normal projection code.
  2. The rebuild runs the evaluation gate on the new graph and records the result.
  3. Redeploy pointing at the new graph, with new consumer group names (CG_CONSUMER_GROUP_*). New groups read from the start of the ledger, so nothing written during the switch is lost.

Evaluation gate

Every domain pack ships with an evaluation set: questions with the nodes they should return. A pack's intents aren't served until it passes on the live graph (python -m context_graph.ontology evaluate --record) or a rebuild passes. Until then, asking for one of its intents returns 409, and responses list it under meta.eval_pending. Changing a pack's retrieval section puts it back to pending.

Ontology

The PDLC ontology

PDLC (product development lifecycle) is the first real domain pack. It lets an agent follow work from a request, through code, tests and shipping, to incidents and lessons. Every answer cites the events it came from.

Common mix-up. There are no Epic, Story, PR, Commit, File, Build or Environment types. Epics, stories, tasks and bugs are all a WorkItem with a work_type. A pull or merge request is a Change, and its commit SHAs and files are properties on it. Environment is a property of Deployment. CI shows up as TestRun.

The main chain

Arrows follow the edge direction stored in the graph. Dashed arrows are trace links, which can be proposed or confirmed.

17 node types in eight groups

Every node's ID is built from its key fields, for example Change:acme/payments|7 or WorkItem:jira|PAY-341. The same ID from two sources means the same node.

Group Types What they hold
Intake Request, Spec, Requirement, DesignElement The ask, the current contract, single requirement statements, HLD and LLD sections
Plan WorkItem A ticket: epic, story, task, bug or production change
Build Change, Review A pull or merge request with its SHAs and files; a review verdict
Verify TestCase, TestRun A test, and one run of it against a commit
Ship Release, Deployment, Component A library release, one deploy to an environment, a service or module (file path prefixes map files to it)
Operate Incident Severity, environment, what was running
Knowledge Decision, Constraint, Lesson Why we did it, rules for future work (pinned, never decayed), what we learned
Org Team Owner group

The other edges:

  • DEPENDS_ON between work items or components.
  • TOUCHES from a change to a component, and REVERTS from one change to another.
  • DEPLOYED_TO, AFFECTS, REMEDIATES and RAISES around deployments and incidents.
  • DECIDED_BY, CITES, AMENDS and CONSTRAINS around decisions and constraints, plus OWNED_BY for ownership.
  • From the common layer it extends SUPERSEDES, CONTRADICTS, SAME_AS (two tools' tickets for the same work) and REFERENCES (an agent event that mentions a PDLC node).

Five question types (intents)

Intent Example question
trace Where is PAY-341 deployed right now?
completeness Which requirements for the next release still have no tests?
status Is this section of the refunds HLD still the approved version, and what replaced the old one?
impact Have we tried this fix before, and did it get reverted or cause an incident?
preflight Before I edit refund/retry.py, what should I know?

Three rules that shape every answer

  • Trace links are proposed or confirmed. Eight edges carry a confidence and a status. A link a tool declared, such as "Fixes PAY-341" in a change description, starts confirmed. An inferred link starts proposed. Nothing is thrown away on write; the confidence cut-off is applied on read. An LLM may only propose knowledge and link edges, never facts like a Change or a Deployment.
  • Superseded things drop out. A decision that is superseded or reversed, or anything another node SUPERSEDES, is left out of answers. For status and why questions it's shown and marked as superseded.
  • Trust comes from the source, not the content. Webhook sources ingest under a reserved agent ID that the public API refuses, so an API client can't pose as a trusted tool. Untrusted items that nothing trusted backs up stay out of the agent's working context.

Worked example: a change is merged

The code host reports change #7, "Fix refund retry", with the description "Fixes PAY-341" and merge SHA def456. The webhook adapter checks the signature and emits pdlc.change.merged. The pack rule then:

  1. Upserts Change:acme/payments|7 with its title, description and merge SHA, and moves it to merged.
  2. Adds a confirmed IMPLEMENTS edge to ticket PAY-341. If the ticket hasn't arrived from the issue tracker yet, a stub is created.
  3. Links any deployment already seen for commit def456 with DEPLOYS. That edge is what answers "Where is PAY-341 deployed?"
  4. Adds DERIVED_FROM back to the source event, so the answer can cite it.

How it is evaluated

Eval set Size Mean F1 Pass mark
Tool event fixtures 11 questions 1.00 0.95
Apache OpenDAL project history 17 questions over 288 merged changes and 4 releases 0.91 0.90
Synthetic payments project Supersession, completeness and negation questions 1.00 each (keyword search: 0.53, 0.17, 0.67) n/a

Known gaps.

  • The tool event fixtures are hand-written, not recorded from a real project.
  • Deployment, TestRun and Lesson haven't been checked against real data.
  • A change that references an issue by number (#12) doesn't link yet; only tracker keys like PAY-341 do.
  • With no service catalog importer, TOUCHES stays empty.
  • Aggregate, time-window, similarity and snapshot questions can't be answered yet.
  • Some pack settings (decay, embedding fields, vocabulary mappings) are declared but not yet read by the engine.

Flows

Ingestion

The ledger's role hasn't changed: an append-only source of truth. What's new is a wider front door, workers that no longer depend on Redis, and a projection step that asks the ontology what to write.

1. Ways in

  • POST /v1/events and /v1/events/batch (up to 1,000 events) for agents and SDKs.
  • POST /v1/events/import for admins: gzip NDJSON, up to 500,000 events, appended in time order after everything already in the ledger.
  • POST /v1/webhooks/{source} for tools. The request's signature is checked, and an adapter translates the payload into a pack event such as pdlc.change.merged. A redelivered webhook gets the same event ID, so it's deduplicated.

2. Checks

  • A domain pack owns its event namespace. An undeclared pdlc.foo gets 422. Agent namespaces stay open.
  • Body size limits apply before and after decompression.
  • A per-client quota (default 60,000 events a minute) answers 429 with Retry-After.
  • The public API refuses the reserved webhook agent IDs, so a client can't claim to be a trusted tool.

3. Ledger: the EventLog port

Dedup is now part of the port's contract: appending the same event ID twice returns the original position. Each backend keeps that promise in its own way. On Redis it's the Lua ingest script. On Spanner it's a read and a write in one transaction. Every event comes back with its own outcome: created, duplicate or failed.

Ingest contract change. Responses now include a status for each event. A batch where nothing was stored answers 422 (all refused) or 503 (store failed) instead of 201. Clients that only checked for 201 should be reviewed.

4. Workers: the Subscription port

Workers used to call Redis stream commands directly. Now the base worker talks to the Subscription port, so the same loop runs on every backend:

  1. Drain pending. Re-process items this consumer was given but never acknowledged. Each pending item is read once per sweep, and an item that keeps failing is dead-lettered instead of being retried forever.
  2. Read new items, process them, and acknowledge them.
  3. Claim orphaned items from consumers that died.
  4. Retry outages in place. If storage is unavailable or times out, the worker waits and retries (200 ms, doubling up to 10 s). These failures never count towards dead-lettering, and log order is kept.
  5. On idle, flush anything still buffered, so the last few events aren't left unprojected when traffic stops.

5. Projection: two steps in one flush

The projection worker buffers events and writes them in flushes. Each flush does both kinds of projection:

  1. Structural (unchanged code). Event nodes, plus FOLLOWS and CAUSED_BY edges. The previous event in a session is now looked up from the ledger when it's not in memory, so FOLLOWS edges survive restarts and extra replicas.
  2. Pack rules (new). For events a pack has rules for, a pure function (no I/O) turns each event into a plan. The whole flush is then written in four steps: upsert nodes, change states, resolve lookups, upsert edges.

Batching made projection much cheaper. On the OpenDAL history, graph calls per event fell from 5.01 to 0.14, and ledger calls from 1.01 to 0.03, producing the same graph.

What every pack write guarantees

  • Stable identity. IDs come from key fields, so two sources naming the same thing land on the same node.
  • Provenance and trust. Every node gets DERIVED_FROM to its event, and records source_trust.
  • Late events can't undo state. A state change says which states it may move from, so a late "opened" event doesn't undo a merge.
  • Arrival order doesn't matter for links. A merge links to an earlier deployment of its commit, and a deployment links to an earlier merge.
  • Missing endpoints become stubs that are filled in when the real event arrives.
  • One bad event doesn't block a batch. If a flush fails for a reason other than an outage, the worker retries one event at a time and dead-letters only the bad one.

6. Extraction

A separate consumer group, pack-extraction, asks an LLM for proposals using each pack's extraction profile. Proposals are capped in confidence, never marked confirmed, and never overwrite an existing node or link. A decision extracted by the LLM and the same decision recorded by a tool end up as one node, because both are keyed by a hash of the content.

Retrieval

There are now two retrievers. The agent-memory engine answers the existing endpoints. The artifact retriever is new and answers questions about domain things like tickets, changes and deployments.

Endpoint Served by Contract
GET /v1/context/{session_id} Retrieval engine Unchanged
POST /v1/query/subgraph Retrieval engine Unchanged
GET /v1/nodes/{id}/lineage Retrieval engine Unchanged

All responses use the Atlas shape. The only additions are a new meta.eval_pending list, and provenance.source, which can now be memory or spanner as well as redis.

What the refactor changed in the agent-memory engine

Aspect Before After
Where it lives Inside the Neo4j adapter, mixed with Cypher Its own engine, with no database code
Storage calls Neo4j driver and RediSearch directly Three read ports: GraphReads, KeywordIndex, VectorIndex
Intents and edge weights Fixed keyword and weight tables in code Read from the common-layer packs (same values, tested to be equal)
Keyword channel Returned nothing in practice (see below) Fixed: searchable text built at ingest, any query word can match
Algorithms Unchanged. Fusion (RRF), PageRank (PPR), diversity (MMR), query expansion (HyDE) and decay scoring were already pure Python. They moved, they weren't rewritten.

Subgraph query, step by step

  1. Intent. From an LLM classifier if one is configured, otherwise from the packs' keywords. The caller can also name the intent. The intent picks the edge weights and the seed strategy.
  2. Three seed channels, in parallel. Graph seeds from GraphReads, keyword seeds from KeywordIndex, and vector seeds from VectorIndex (entity embeddings, similarity at least 0.5). If one channel fails, the others still answer, and meta.retrieval_channels shows the count from each.
  3. Fuse. Reciprocal rank fusion (k = 60) merges the three lists by rank and keeps the top 10.
  4. Expand. For who_is, personalize and related questions, events from other sessions about the same entities are added. Then each seed's neighbours are read in one batched call. Added nodes are marked proactive.
  5. Score and rank. Every node gets the four-factor decay score (recency, importance, relevance, user affinity). Personalised PageRank can blend in, but it's off by default (CG_PPR_ENABLED). MMR adjusts only the relevance score for diversity. Results are sorted by decay score and cut to max_nodes.
  6. Respond. Access counts are bumped, and the Atlas response is built with provenance and meta.

Session context (GET /v1/context/{session_id}) is simpler: read the session's events a page at a time, score them by decay, and return the top max_nodes with the edges between them. There's no intent step and no seeds. Lineage follows CAUSED_BY paths from a node within depth limits. On Spanner, it's one graph (GQL) query.

Two behaviour changes to know about.

  • The keyword channel now works, so rankings can change. Before, the Redis index looked at fields events don't have, and it required every word in the question to match, so it returned almost nothing. Now each event gets searchable text built once at ingest from its tool name and payload, and a query matches on any meaningful word. Older events aren't backfilled, and the ranking change hasn't been measured yet.
  • The evaluation gate doesn't cover this engine. Domain intents such as trace and status never reach it; it only uses the common-layer intents. Pack weight additions to why and who_is are included, but they should have no effect here because the engine only walks edges leaving events. That last point isn't covered by a test.

Artifact query, step by step

The artifact retriever is a separate component. It reads through the PackGraph port and shares only the response models with the engine. It uses no fusion, PageRank or decay.

  1. Gate. Packs that haven't passed evaluation are left out. Naming one of their intents returns 409.
  2. Intent from the pack keywords, or passed by the caller.
  3. Seeds. Exact references first: ticket keys like PAY-341, file paths, version tokens, #7, and the pack's ID patterns. Rare words are used only when no ID matches.
  4. Walk. Only edges between pack types are followed, in the intent's direction, level by level within limits. Two rules stop drift. The walk won't hop to siblings through a shared node (change, then its release, then every other change in that release). It also won't wander into the family of a node it reached (change, then its ticket, then that ticket's epic).
  5. Admission. Superseded items are dropped, except for status and why questions. Untrusted items need a trusted link to stay in. Proposed links stay, with their confidence.
  6. Completeness questions skip the walk and compute a set difference. Each subject comes back as no_link, proposed_only or confirmed.
  7. Bounds. Each request has a budget of graph calls (400) and query terms (16). truncated is set when a limit cut the answer, and a timeout returns 504.
Storage

How Engram talks to Spanner

Engram's application code never calls Spanner directly. The API, the workers and the two retrievers call storage ports. A backend is a set of classes that implements them.

The five contracts

Port What it promises Main methods Called by
EventLog Idempotent append: the same event twice returns the original position. Positions are opaque and ordered. append_batch_outcomes, get_documents, read_after, previous_in_session, search_bm25, trim, expire Ingest, workers, retention, migration
Subscription A consumer group over the log. At-least-once delivery, in order within a session, no order promised across sessions. read_new, read_pending, ack, claim_orphaned, dead_letter, lag The base worker only
GraphBackend Merge-style idempotent writes; an edge to a missing node writes nothing; reads are bounded. It bundles the graph store, maintenance, user store, PackGraph and GraphReads. upsert_nodes, upsert_edges, change_states, find_latest, neighbors; reads.seed_events, reads.event_neighbors, reads.lineage_chains Workers write; the engine reads only GraphReads; the artifact retriever reads PackGraph
KeywordIndex Text search, scores normalised to 0 to 1 search(text, session_id, limit) Retrieval engine
VectorIndex Nearest neighbours by embedding, scores 0 to 1, best first nearest(embedding, top_k, threshold) Retrieval engine

All backends raise the same errors: StorageError, with ConflictError, NotFoundError, UnavailableError, StorageTimeoutError and InvalidRequestError under it. Spanner's exceptions are mapped onto these. An aborted transaction becomes UnavailableError, which the workers retry in place.

Choosing a backend

CG_STORAGE_EVENT_LOG=spanner      # redis | memory | spanner
CG_STORAGE_SUBSCRIPTION=spanner   # must match the event log
CG_STORAGE_KEYWORD_INDEX=spanner  # must match the event log
CG_STORAGE_GRAPH=spanner          # neo4j | memory | spanner
CG_STORAGE_VECTOR_INDEX=spanner   # must match the graph
CG_SPANNER_PROJECT=... CG_SPANNER_INSTANCE=... CG_SPANNER_DATABASE=...

One factory reads these settings and hands the API and the workers one object per port. If any port uses Spanner, they all share one database handle. A sixth setting, CG_STORAGE_ARCHIVE (fs or gcs), predates this work and picks where expired events are archived. A unit test fails the build if anything outside the storage adapters imports a Redis, Neo4j or Google Cloud client.

How each port maps onto Spanner

Everything lives in one Spanner database: the ledger, the consumer-group state and the graph.

Port Spanner shape
EventLog Events table keyed by the event's random UUID, so writes spread evenly. Each row records the commit timestamp and a shard (a hash of the session ID, 16 shards), so one session's events stay together. Position is commit_ts / batch_index / event_id. Dedup is a read and a write in one transaction.
Subscription Consumers poll. read_new runs in a read-write transaction: it reads events past the group's per-shard cursor, records them in ConsumerDeliveries and moves the cursor. ack deletes delivery rows. lag counts undelivered rows. Dead letters have their own table.
GraphBackend Two tables, GraphNodes (label, ID, properties as JSON, embedding) and GraphEdges, declared as one property graph. Spanner and the in-memory backend share a generic graph layer built on eight primitives: get, find, upsert and delete for nodes and for edges. Lineage and entity similarity use native Spanner features. Everything else is key and index reads.
KeywordIndex A Spanner full-text search index over the event's searchable text, queried with SEARCH and SCORE
VectorIndex A cosine vector index on the embedding column (384 dimensions), queried with APPROX_COSINE_DISTANCE 
CREATE PROPERTY GRAPH EngramGraph
  NODE TABLES (GraphNodes KEY (label, node_id)
      DYNAMIC LABEL (label) DYNAMIC PROPERTIES (props))
  EDGE TABLES (GraphEdges KEY (src_label, src_id, edge_type, dst_label, dst_id)
      SOURCE KEY (src_label, src_id) REFERENCES GraphNodes (label, node_id)
      DESTINATION KEY (dst_label, dst_id) REFERENCES GraphNodes (label, node_id)
      DYNAMIC LABEL (edge_type) DYNAMIC PROPERTIES (props))

One event, end to end on Spanner

  1. Ingest. The API validates the batch and appends it. Each transaction writes Events rows with the commit timestamp and returns an outcome for each event.
  2. Deliver. A worker's read_new moves its group's cursor and gets back event IDs.
  3. Project. The worker fetches event bodies, looks up the previous event in the session for FOLLOWS, and writes nodes and edges through the graph port.
  4. Ack. The delivery rows are deleted.
  5. Enrich. Embeddings are written to the embedding column, which feeds the vector index.
  6. Retrieve. Keyword seeds come from the search index, vector seeds from the vector index, and graph reads from key and index reads (GQL for lineage). Ranking and the response are the same code as on every other backend.

Guardrails

  • Commit budget. Spanner caps a commit at 80,000 mutations and 100 MiB. Engram aims for half of each, estimating the cost of each row (an event about 33 mutations, a node 11, an edge 18). A ledger split keeps order: if a later part fails, that part and everything after it is reported failed. A graph write that turns out too large is rolled back and halved.
  • No surprise databases. A database is created automatically only on the emulator. A real instance needs CG_SPANNER_ALLOW_CREATE_ON_INSTANCE=true, and instances are never created. At start-up the expected tables, indexes and property graph are checked, and a mismatch stops start-up.

How it is verified

  • Conformance suites. One test suite per port runs against every backend: in-memory always, and Redis, Neo4j and the Spanner emulator as integration tests. The retrieval engine is run on each backend too.
  • Dual run. Neo4j as primary and the Spanner emulator as secondary, compared on the ledger, the graph and retrieval answers: no differences.
  • Behaviour probes on the emulator. Retrieval answers matched the in-memory backend on 22 of 22 evaluation questions. Search returned the same results on 11 of 11 queries. Vector recall@10 was 1.0.
  • Real-instance trial. 8 producers wrote 2,070 events. Two consumer groups each received all of them, with nothing missing, duplicated or out of session order.

Moving data from Redis to Spanner

python -m context_graph.migration copy    --to spanner   # copy the ledger until caught up
python -m context_graph.migration mirror  --to spanner   # keep copying (dual run)
python -m context_graph.migration compare --to spanner --graph   # non-zero exit on any difference

The mirror reads the Redis ledger in order and imports it into Spanner. Each event keeps its original position as legacy_position, so a copy can resume where it stopped. It won't run if Spanner already holds events written there directly. The graph isn't copied: Spanner's own projection worker rebuilds it from the imported ledger. Cutover needs a short pause in ingest, because the API writes to one side only.

Spanner insights

Lessons from the design, the emulator and the real instance that matter for anyone taking this further.

1. One database, but the graph stays disposable

The ledger and the graph share a database but never a transaction. That keeps the original promise: the graph is derived from the ledger and can be rebuilt at any time. It also means a single Spanner instance can replace both Redis and Neo4j without coupling their failure modes.

2. Dynamic labels make packs cheap on Spanner

Nodes and edges carry their type as a value (a dynamic label), and properties live in JSON. A new pack type is just a new label value: no new table and no DDL. The price is that JSON properties have no secondary indexes, so finding nodes by a property scans every node with that label. Hot pack keys will need generated columns with indexes once data grows.

3. The emulator is not Spanner

Three differences showed up, and only the real instance revealed them:

  • Real Spanner rejects about 1 in 1,000 ordinary decimal numbers in JSON columns, and one bad value fails the whole write. Floats are now stored tagged as {"$float": "..."}.
  • GQL label filters such as (a:Event) matched nothing on the real instance. Queries now filter on the label and edge_type columns. The cause is unknown, so new GQL should follow the same rule.
  • The emulator runs transactions one at a time, so it can't show lock contention.

Anything that matters on Spanner has to be proven on a real instance.

4. The trial measured the network, not Spanner

Calls took about 0.4 to 1.4 seconds each (append 1.4 s, read 0.67 s, ack 0.65 s, 200-node flush 0.69 s). The client ran in an unknown region away from the instance, so these are mostly round trips. The trial's 54 events a second is a client limit, not a Spanner limit. A test from a client in the same region is needed before drawing any capacity conclusions.

5. The subscription is the piece to watch

Consumers poll, and read_new reads across all 16 shards inside a read-write transaction. That's what guarantees no event is skipped, but it may contend with ingest under load. Shards keep each session's events in order; they don't spread the read work across consumers. Load testing at 100 and 1,000 events a second should focus here first.

6. Plan the operations work

Still missing: a way to change the schema in place (today it's only checked at start-up), a CI job against the emulator, IAM design, metrics, backups and point-in-time recovery. A blue/green pack rebuild needs a second database, which hasn't been tried. The smallest Enterprise instance (100 processing units) is about $90 a month plus storage, and a 90-day free trial instance exists. These prices haven't been checked against a live price list.
